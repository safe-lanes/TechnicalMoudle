**PROMPT TO REPLIT (PMS STATUS & LOGIC AUDIT)**

You are auditing an existing **Planned Maintenance System (PMS)** web application for ships.
The code is already written in this Replit project but has **many bugs, missing pieces, and TODOs**.

👉 **Your task is NOT to write new code now.**
Your task is to **read the current codebase** and give me a **clear, honest status report** of how the system is actually working today.

I want to know your **current understanding, data linking, and process flow for each sub-module**, based ONLY on the code that exists.

---

### 1️⃣ Scope – Modules to Analyse

Go through the repo and cover at least these modules (names may vary, use closest matches):

1. **Components module** (Equipment / Component Register)
2. **Work Orders module**
3. **Running Hours module**
4. **Spares module**
5. **Stores / Lubes / Chemicals / Others module**
6. **Modify PMS / Change Request module**
7. **Admin module** (PMS settings, master data, lead time, grace, etc.)
8. **Fleet Admin / Fleet Data / Bulk Import**
9. **Reports module**
10. **Certificates & Surveys / Technical module** (even if incomplete)

If there are additional PMS-related modules you find, include them too.

---

### 2️⃣ For EACH Module – Answer These Questions

For every module above, give me a structured answer with these headings:

#### 2.1 Purpose & Screens

* **What is this module supposed to do**, based on its React components, routes, and naming?
* **What main screens/components exist?**

  * Give file names and route paths (e.g., `ComponentsPage.tsx`, `/components`).
* Briefly describe what each screen shows and what actions the user can perform (according to current code, not theory).

#### 2.2 Data Models & Tables

* Which **database tables / entities** does this module use?

  * e.g., `components`, `jobs`, `work_orders`, `spares`, `stores`, `pms_settings`, etc.
* For each table:

  * List the **key fields** that this module reads or writes.
  * Specify the **primary linking fields** (e.g., `component_id`, `job_id`, `vessel_id`).

#### 2.3 API Endpoints Used

* List the **backend API endpoints** this module calls:

  * e.g., `GET /components`, `POST /work-orders`, `PUT /spares/:id`, etc.
* For each endpoint:

  * What does the front-end expect from it? (request payload + response shape)
  * Is the endpoint **fully implemented**, partially implemented, or stubbed with mock data?

#### 2.4 Process Flow – As Implemented in Code

Describe the **actual process flow** in this module, for example:

* Components:

  * How components are loaded, displayed, filtered.
  * How Add/Edit component works in current code.
* Work Orders:

  * How WOs are created (planned / unplanned) in current implementation.
  * What fields are saved in Part A and Part B.
  * How status changes (DUE / OVERDUE / COMPLETED / POSTPONED) are handled in code.
* Running Hours:

  * How RH are edited (single vs bulk).
  * How RH changes are saved and whether anything else is triggered.
* Spares / Stores:

  * How ROB is updated.
  * How consumption and receipt are handled in current code.
  * Whether multi-location (A/B) is actually implemented or just in UI.

Explain **step by step**, based only on implemented logic in the repo.

---

### 3️⃣ Cross-Module Linking – What the Code Actually Does

I want a separate section on **inter-module linking** as it exists TODAY in code:

Answer these specifically:

1. **Jobs ↔ Components**

   * How does a job link to a component in the database?
   * Which fields are used? (`component_id`, `component_code`, etc.)
   * When a component is edited/deleted, what happens (in code) to its jobs?

2. **Work Orders ↔ Jobs & Components**

   * When a WO is created, what data is copied from Job/Component into Part A?
   * Does the WO creation code enforce “one active WO per job+component” or allow duplicates?

3. **Work Orders ↔ Running Hours**

   * Does completing a WO update any RH fields?
   * Does RH module logic read anything from WO history?

4. **Work Orders ↔ Spares**

   * When a WO is completed:

     * Is there code that deducts spare ROB?
     * Does it ask for location (A/B) or use some default?
   * Is the deduction logic fully implemented or partly TODO?

5. **Spares ↔ Components**

   * How are spares linked to components in the DB?
   * Is one spare linked to multiple components in the current implementation, or one-to-one?

6. **Fleet Admin ↔ Vessel Data**

   * Is there any working mapping logic from fleet templates to vessel components/jobs/spares?
   * Or is it mostly UI only / TODO?

7. **Admin PMS Settings (Lead Time & Grace) ↔ WO Generation**

   * Are there any implemented settings for lead time / grace?
   * Are these values actually used anywhere in WO auto-generation logic, or not yet?

---

### 4️⃣ Status of Missing / TODO / Mock Behaviour

For each module, I also want a **“Status” subsection**:

* **What is working:**

  * Features that are actually wired end-to-end (front-end → API → DB).
* **What is partially implemented:**

  * Screens that show data but don’t save.
  * Buttons that open modals but don’t hit real endpoints.
  * Endpoints that return mock data.
* **What is clearly unfinished or stubbed:**

  * TODO comments.
  * Functions named but returning `null`/`[]`/hard-coded data.
  * “Not migrated” methods in `PostgresStorage` or similar.

Be very explicit:
Name the file, the function, and what is missing.

Example style:

* `SparesNew.tsx` → Bulk update modal UI exists, but calls no real mutation; currently only logs to console.
* `server/storage.ts: purgeJobsAndLinkedData` → Declared but not implemented, so deleting a job will NOT clean linked WOs.

---

### 5️⃣ Very Important – No Hallucinations

Rules:

* Base EVERYTHING on the actual code in this Replit project.
* If something is **unclear** or there are **two possible interpretations**, say:

  * “Unclear – code does X, but name suggests Y.”
* If a feature **does not exist in code**, do **NOT** describe intended behaviour.
  Just say: “Not implemented in this codebase.”

I am using this report to decide where the real bugs and gaps are,
so **honesty > optimism**.

---

### 6️⃣ Output Format

Return your answer as:

1. **Module-by-module sections**:

   * `1. Components Module`
   * `2. Work Orders Module`
   * `3. Running Hours Module`
   * …

   Each with:

   * Purpose & Screens
   * Data Models & Tables
   * API Endpoints Used
   * Process Flow (as implemented)
   * Status (working / partial / stubbed)

2. Then one section:

   * `Cross-Module Linking – Actual Behaviour in Code`

3. Then one final section:

   * `Summary – Biggest Gaps & Risks Detected`

---

Use as much detail as needed; this is for a **deep technical audit**, not a high-level summary.
