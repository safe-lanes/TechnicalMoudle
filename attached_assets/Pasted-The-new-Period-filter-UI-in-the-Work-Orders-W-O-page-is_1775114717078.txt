The new Period filter UI in the Work Orders (W.O) page is implemented, but the filtering is currently incomplete.

It is filtering calendar-based work orders, but it is not properly filtering running-hours-based work orders.

This must be corrected.

Core issue
The Period filter cannot behave as a calendar-only filter.

The Work Orders module contains both:

Calendar-based work orders

Running-hours-based work orders

If the filter only works for calendar jobs, then the data shown to the user is incomplete and misleading.

That is not acceptable.

Required correction
Make the Period filter a complete filter for the Work Orders module by ensuring it also includes Running Hours based work orders using the proper PMS business logic.

Required RH logic
For Running Hours based work orders, the period filter must use the logic:

number of days × 24 hours

This logic must be used to determine future RH jobs within the selected period.

Business understanding
For calendar jobs, filtering by Due Date is straightforward.

For RH jobs, the system cannot rely on a normal calendar due date in the same direct way.
Instead, it must determine whether an RH work order falls within the selected future period by converting the selected time window into hours.

Meaning
If the selected period covers N days into the future, then for RH jobs the system should evaluate using:

N days × 24 hours = N-hour equivalent window

This is the core logic needed so RH jobs also appear correctly inside the selected period.

What this means functionally
When the user applies a Period filter:

calendar-based jobs should continue to be filtered by the relevant work order due-date logic,

running-hours-based jobs must also be evaluated against the selected period by translating that period into an hour window.

Example understanding
If user selects a future period equivalent to 30 days,
then RH logic should treat that as:

30 × 24 = 720 hours

and RH-based work orders that fall due within that 720-hour equivalent window must also be included.

This is the same principle that makes RH future planning meaningful in PMS.

Why this matters
Without RH inclusion:

user sees only calendar-based work orders,

RH-based future jobs are missing,

filter output becomes misleading,

planning decisions become wrong.

The Period filter must therefore become a common operational planning filter, not just a date-only calendar filter.

Expected behavior
The Period filter should return a correct combined result set containing:

calendar-based WOs matching the selected period

RH-based WOs matching the same period through day-to-hour conversion logic

Detailed implementation expectation
Please review the current filtering logic in the Work Orders page and extend it so that:

For Calendar-based jobs
Use the current period filter logic based on the relevant due-date field already used in the module.

For Running Hours based jobs
Use equivalent future-window logic based on selected period length.

Convert selected period to number of days
From the selected Period filter, derive the total selected period span in days.

Examples:

Year only → selected date span of that year

Year + Quarter → selected date span of that quarter

Year + selected month(s) → selected date span covering those month selections

Date Range → direct day difference between from-date and to-date

Then convert to hours
selectedPeriodDays × 24 = selectedPeriodHours

Then apply RH inclusion logic
RH work orders that are due within that computed future-hours window must be included in the filtered result.

Please do not take a shortcut by simply excluding RH jobs when Due Date is empty or non-standard.

That is exactly the current problem.

Instead, explicitly include RH-based WOs using RH period-equivalent logic.
