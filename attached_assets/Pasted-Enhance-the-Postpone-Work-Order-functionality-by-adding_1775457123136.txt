Enhance the Postpone Work Order functionality by adding an “Other Reason” option to the postponement reason dropdown, so users can enter a custom reason in the text box below when the predefined list does not cover the situation. The current dialog already shows a reason dropdown and a remarks/details text box, so this change should extend the existing UI without redesigning it.
​

Objective
The postponement reason dropdown is now linked to Master Lists, which is good for reporting and filtering. However, there will be real cases where the required reason is not available in the configured list. To handle that, add an “Other Reason” option in the dropdown and use the text box below for mandatory custom input only when that option is selected.
​
​

Required behavior
In the Postpone Work Order dialog:

Keep the existing Reason for Postponement dropdown

Keep the text box below it in the same UI position

Add a dropdown option named Other Reason

When the user selects Other Reason, the text box below becomes mandatory

When the user selects any standard master list reason, the text box remains optional and acts as supporting remarks/details

Keep the current UI layout, spacing, labels, and style unchanged as much as possible
​

Source of dropdown values
Continue loading standard postponement reasons from Master Lists

Append Other Reason as an extra selectable option in the dropdown even if it is not part of the master list dataset

Standard reasons should still come from the existing master list API and respect active/inactive status and display order

Other Reason should always appear in the dropdown, preferably at the end of the list
​

Validation rules
Implement the following validation:

A dropdown reason selection is always mandatory

If the selected value is Other Reason, then the text box below is mandatory

If Other Reason is selected and the text box is empty or only whitespace, the user must not be able to confirm postponement

Show a clear validation message such as: Please enter the custom postponement reason

If a standard master-list reason is selected, the text box should remain optional
​

Field behavior
Use the existing text box below the dropdown for two purposes:

For standard reasons: optional Remarks / Additional Details

For Other Reason: mandatory Custom Postponement Reason

You may either:

keep the same label and change helper text/placeholder dynamically, or

change the field label dynamically based on selection

Preferred behavior:

If standard reason selected, placeholder: Enter additional remarks or details...

If Other Reason selected, placeholder: Enter custom postponement reason...
​

Data handling
Store postponement data in a way that preserves both reporting and flexibility:

If a standard reason is selected:

save the selected master-list reason as postponementReason

save the textbox content as postponementRemarks if entered

If Other Reason is selected:

save postponementReason as Other Reason

save the user-entered text box value as postponementRemarks or customPostponementReason, depending on the current schema and what best fits existing implementation

Do not break existing records or reporting flows

Keep backward compatibility with current postponement records
​

Work Orders listing / filtering behavior
Because the Work Orders page already includes a Postponement Reason filter, keep reporting behavior structured:

Standard reasons should continue to be filterable as before

Other Reason should also appear as a filterable value wherever postponement reason is shown

If needed later, users can review the detailed custom text in the remarks/details area or work order detail view

Do not attempt to add every custom text as a new filter option; only the main reason should be filterable as Other Reason
​

Master list behavior
Do not require Other Reason to be created and maintained as a normal editable master-list record unless that is the easiest implementation path

If technically better, you may inject Other Reason in frontend after fetching master list values

Standard reporting reasons must still remain master-list-driven

Do not disturb existing Master List CRUD behavior for normal postponement reasons

UI expectations
Keep the same modal design already shown in the current Postpone Work Order popup

Do not redesign the popup

Do not move fields unnecessarily

Use the existing textbox below the dropdown for this logic

Maintain current look and feel of validation, required marking, and spacing
​

Suggested implementation approach
Continue fetching postponement reasons from the master list endpoint

Add Other Reason as a final option in the dropdown data source

Add conditional validation based on selected dropdown value

Add dynamic label/placeholder/help text for the textbox below

Keep backend validation aligned with the new behavior:

standard reason = non-empty dropdown reason required

other reason = non-empty dropdown reason plus non-empty text box required

Acceptance criteria
This task is complete only if:

The Reason for Postponement dropdown includes Other Reason

Standard reasons still come from Master Lists

The textbox below becomes mandatory only when Other Reason is selected

Users cannot submit Other Reason without entering custom text

Standard reasons still support optional remarks/details

Existing postponement flow and UI are not broken

Work Orders filtering/reporting still works correctly with structured reason values

Other Reason entries remain understandable in history/details screens

Important note
The goal is to keep postponement reasons structured for tracking, while still allowing flexibility for cases not covered by the predefined master list. This should be an enhancement to the current design, not a redesign.
