Context:
Our client has asked the following questions about SAIL PMS:

"Can you advise if SAIL PMS has the feature of Centralization of Data? Can you give a high-level description of it?"

Your task is to thoroughly analyze the existing SAIL PMS codebase — covering all modules, database schema, API design, user roles, and data flows — and then produce a structured, client-ready written response that accurately describes how Centralization of Data is achieved within the system.

STEP 1 — Codebase Analysis
Scan the full SAIL PMS codebase and identify all features, modules, and design patterns that support or contribute to Centralization of Data. Specifically look for:

Single Shared Database Architecture

Is there one central database (e.g., PostgreSQL/Supabase) that all vessels and users connect to?

Are vessel records, work orders, components, spares, stores, running hours, jobs, and reports all stored in a single unified schema?

Confirm whether multi-vessel data co-exists in the same tables (e.g., distinguished by vessel_id or similar foreign key).

Multi-Vessel Data Management

How are multiple vessels' data managed centrally?

Is there a Fleet-level view vs. Vessel-level view toggle in the Dashboard?

Does the Bulk Data Import support fleet-wide data upload (check the "Fleet Data Import" toggle in the Admin > Bulk Data Imp screen)?

Role-Based Access Control (RBAC) over Centralized Data

How does the system control who sees which vessel's data?

Are there roles such as Fleet Manager, Vessel Manager, Superintendent, CE (Chief Engineer) etc., each accessing the same central data with different permissions?

Does the Admin panel manage users and their vessel-level access centrally?

Centralized Work Order & Job Tracking

Are work orders from all vessels visible in one place for management-level users?

Does the Management Dashboard (vs. Operational Dashboard) aggregate data across all vessels?

Centralized Spares & Stores Inventory

Are spares and stores managed in a single inventory accessible across vessels?

Is there a central stock visibility (e.g., Spares Stock Status, Critical Spares Stock Status as shown in the dashboard)?

Centralized Alerts & Notifications

Is the Alert Configuration (Critical Job Overdue, Low Critical Spares, Cycle Skipped) managed from a single admin panel and applied fleet-wide?

Are notifications dispatched centrally via email and in-app?

Centralized Reporting

Does the Reports module aggregate data across vessels in a single view?

Is there a 6-Month Maintenance Trend, Overdue WO analysis, Postponed Work Orders, and Top 5 Reasons for Postponement/Overdue visible at fleet level?

Centralized Master Data Management

Does the Admin > Master Data section manage shared lookup data (e.g., job types, categories, manufacturer data, location codes) centrally?

Are these shared across all vessels from one place?

Centralized Modify PMS Requests

Is the "Modify PMS" module managing requests centrally with an approval workflow?

Are Modify PMS Requests YTD tracked centrally?

Audit Trail & History

Is there a centralized import history, alert history, and work order history?

Is data immutable once recorded (audit-ready)?

STEP 2 — Output Required
After the analysis, produce two outputs:

OUTPUT A — Internal Technical Summary (for our team)
A bullet-point technical summary listing:

Which modules contribute to centralization

Any gaps or limitations (e.g., if certain data is vessel-local rather than centralized)

Database architecture notes (single schema, multi-tenant pattern, etc.)

OUTPUT B — Client-Facing Written Response (formal, professional tone)
Write a polished, client-ready response to the following two questions:

Q1: Does SAIL PMS have the feature of Centralization of Data?
Answer: Yes/No + one-paragraph confirmation with specific module references.

Q2: Can you give a high-level description of it?
Write 4–6 paragraphs covering the following dimensions:

Unified Database Architecture — All vessel data resides in a single, secure, cloud-hosted database. Every module (Work Orders, Components, Running Hours, Spares, Stores, Reports) writes to and reads from this central repository.

Fleet-Wide Visibility for Management — The Management Dashboard aggregates key KPIs — overdue work orders, WO status, maintenance trends, spares stock levels — across all vessels in real time. Senior stakeholders (Fleet Managers, Superintendents) can view the entire fleet's health from one screen without switching between vessel-specific systems.

Multi-Vessel Data Segregation with Centralized Control — While data is stored centrally, vessel-level filters and Role-Based Access Control (RBAC) ensure that crew on one vessel can only see their own vessel's data, while shore-based management can see all. Access is governed from a central Admin panel.

Centralized Inventory & Spares Management — Spares and stores inventory is managed centrally, providing visibility into stock levels (OK, At Min, Low) across the fleet. Critical spares status is tracked in real time, enabling proactive procurement decisions from a central procurement team.

Centralized Alerts & Escalation — Alert policies (Critical Job Overdue, Low Critical Spares, Cycle Skipped) are configured once from the Admin panel and apply fleet-wide. Alerts are delivered via both in-app notifications and email, ensuring shore-based teams are immediately informed of any fleet-wide compliance issues.

Centralized Bulk Data Import & Master Data — All data — machinery components, jobs, spares, stores, locations — can be imported centrally via standardized Excel/CSV templates through the Admin > Bulk Data Import module. Master Data (lookup tables, reference data) is managed once and shared across all vessels, ensuring standardization and consistency across the fleet.

Professional, formal English

Avoid technical jargon (no mention of "database tables", "API", "foreign keys", etc.)

Structure with clear headings for each dimension

Length: Approximately 500–700 words for the client response

Tone: Confident and factual — this is a capability description, not a sales pitch

End with a one-line summary statement affirming SAIL PMS's centralized architecture as a core design principle

Deliverable: Both Output A and Output B should be provided as formatted text that we can directly use — Output A for internal review and Output B to be copy-pasted into a client email or proposal document.
