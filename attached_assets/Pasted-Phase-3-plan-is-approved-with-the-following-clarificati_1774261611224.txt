Phase 3 plan is approved with the following clarifications. Address these before writing any code:

Clarification 1 — AE Hours 7-day average source:
The AE_HOURS_SPIKE rule needs a 7-day average of AE running hours. This is not currently stored anywhere. Add aeHoursAvg7Day as a numeric column to nr_fuel_rob (or compute it on the fly by querying the last 7 submitted reports for aeRunningHours). Whichever approach you choose, confirm it before implementing the rule. Do not default to 0 if fewer than 3 data points exist — skip the AE_HOURS_SPIKE check entirely if there are fewer than 3 prior reports.

Clarification 2 — CII Band Drop comparison:
For CII_BAND_DROP, compare the CII rating from the previous submission against the current one. Do this by fetching the second-most-recent nr_cii_tracking record for (vesselId, year) before upserting the new one. Store the previous rating temporarily, then compare after upsert. If no previous record exists (first submission), skip this rule.

Clarification 4 — Auto-resolve scope:
Auto-resolve (system acknowledge) applies ONLY to these 4 alert types when their metric recovers:

HIGH_CONSUMPTION — resolves when consumption ≤ 15% above 7-day avg

VERY_HIGH_CONSUMPTION — resolves when consumption ≤ 25% above 7-day avg

LOW_ROB — resolves when endurance ≥ 10 days

CRITICAL_ROB — resolves when endurance ≥ 5 days

AE_HOURS_SPIKE, CII_BAND_DROP, and NEGATIVE_ROB_RISK must NOT auto-resolve — they require manual acknowledgement from Shore Office / Admin only.

Clarification 5 — vesselId in sidebar badge:
Confirm how vesselId is accessed inside SideMenuBar.tsx for the badge fetch. If it is not directly available in sidebar context, use whichever vessel context / hook already exists in the app (e.g. useVesselContext() or similar). Do not hardcode a vesselId. If no vessel is selected, skip the fetch and show no badge.
