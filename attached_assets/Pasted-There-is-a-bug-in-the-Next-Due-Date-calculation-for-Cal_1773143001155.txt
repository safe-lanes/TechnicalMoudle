There is a bug in the Next Due Date calculation for Calendar-based jobs. After a work order is completed and approved, the Next Due Date is being calculated incorrectly — it is adding double the frequency instead of the correct single frequency interval.

Evidence from live testing:

Case 1:

Job: SEWAGE TREATMENT PLANTS, CHECK — Frequency: 1 Day, Maintenance Basis: Calendar

Actual Completion Date entered by crew: 02-Mar-2026

Scheduled Due Date was: 03-Mar-2026

Expected Next Due Date: 02-Mar-2026 + 1 day = 03-Mar-2026

Actual Next Due Date shown after approval: 04-03-2026 ← Wrong, added 2 days instead of 1

Case 2:

Job: FO PURIFIER INSPECTION — Frequency: 1 Week, Maintenance Basis: Calendar

Actual Completion Date entered by crew: 10-Mar-2026

Expected Next Due Date: 10-Mar-2026 + 7 days = 17-Mar-2026

Actual Next Due Date shown after approval: 24-03-2026 ← Wrong, added 14 days instead of 7

The pattern: In both cases, exactly 2x the frequency is being added instead of 1x. A 1-day job adds 2 days. A 1-week job adds 2 weeks.

Where to look:

Go to the calculateNextDueDate function in shared/dateUtils.ts (or wherever this function lives). Also check workOrderService.ts in the approval path around lines 945–1010 where nextDueDate is updated after approval.

The bug is likely one of these causes:

The function is being called twice — once somewhere in the service and once again in a hook/listener, so the date gets shifted twice

The frequency is being added to the already-calculated next due date instead of to the completion date — meaning it is adding frequency to a date that already had frequency added

The Layer 2 "original due date anchoring" logic is interfering — if the code first calculates a date using the original due date, and then adds frequency on top of that result, it could overshoot

The frequency value is being doubled somewhere — e.g., frequencyValue * 2 or frequencyValue + frequencyValue accidentally

What the correct logic must be — simple and clear:

text
newNextDueDate = completionDate + (frequencyValue × frequencyUnit)
That is it. Nothing else. No anchoring to original due dates. No rolling forward from old dates. Just:

Take the date the crew actually completed the job

Add exactly one frequency interval

That is the new next due date

Examples of correct results:

Completion 02-Mar-2026 + 1 Day → Next Due: 03-Mar-2026

Completion 10-Mar-2026 + 1 Week → Next Due: 17-Mar-2026

Completion 10-Mar-2026 + 1 Month → Next Due: 10-Apr-2026

Completion 10-Mar-2026 + 3 Months → Next Due: 10-Jun-2026

This rule applies ONLY to Calendar-based jobs. Running-hours-based jobs have a different calculation (based on hours, not dates) — do not touch that logic.

What to fix:

Find the calculateNextDueDate function and verify it is doing exactly completionDate + 1 frequency interval — nothing more

Find every place in the approval/completion code path where nextDueDate is written to the database — make sure it is only being set once, not twice

Remove any logic that anchors the next due date calculation to the original/scheduled due date — use only the actual completion date as the base

After fixing, test with:

A 1-day job completed on 10-Mar-2026 → should show 11-Mar-2026

A 1-week job completed on 10-Mar-2026 → should show 17-Mar-2026

A 1-month job completed on 10-Mar-2026 → should show 10-Apr-2026

Fix this and tell me when done.
