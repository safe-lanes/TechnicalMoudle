LAYER 7: RUNNING HOURS (RH) VALIDATION AND ISOLATION SYSTEM

CRITICAL PROBLEM TO SOLVE:

Currently, when crew members complete work orders and enter Running Hours (RH) values, the system has two major flaws:

PROBLEM 1 - Data Corruption: The work order RH entries are overwriting the main Running Hours data in the RH module, destroying the single source of truth for current machinery running hours.

PROBLEM 2 - No Validation: Crew can enter any RH value (realistic or not) without validation. They can enter physically impossible values that violate the basic law that machinery cannot run more than 24 hours per day.

Example of Current Problem:

text
Timeline:
March 1, 2026  → RH Module updated: Main Engine = 500 hours
March 11, 2026 → RH Module updated: Main Engine = 620 hours (current actual value)

Crew backdates a work order to March 9, 2026 and enters:
  - Completion Date: March 9, 2026
  - Running Hours: 850 hours

Current System Behavior (WRONG):
✗ System accepts RH = 850 hours (no validation)
✗ System overwrites the main RH module data
✗ Main Engine RH in RH module changes from 620 to 850
✗ All calculations are now corrupted
✗ The 850 hours violates physical laws:
    From March 1 (500 hrs) to March 9 = 8 days
    Increase = 850 - 500 = 350 hours
    Maximum possible = 8 days × 24 hrs/day = 192 hours
    350 > 192 → PHYSICALLY IMPOSSIBLE but system accepted it!
OBJECTIVE:

Implement a comprehensive Running Hours validation and isolation system that:

Isolates Work Order RH from RH Module - Work orders only store RH snapshots, never write back to RH Module

Validates RH entries against timeline - Ensures entered RH values are physically possible (max 24 hrs/day increase rate)

Cross-checks with all historical data - Validates against both past and future RH entries

Provides real-time feedback - Shows crew the valid RH range as they type

Creates anomalies for suspicious patterns - Flags high utilization rates (>20 hrs/day average) for review

DETAILED IMPLEMENTATION REQUIREMENTS:

1. DATA ARCHITECTURE CHANGES:

A. RH Module Isolation:

The RH Module must become the ONLY place where actual current running hours are stored and updated. Create clear separation:

RH Module Collection (runningHours or similar):

Stores actual current RH for each machinery

Has complete history/log of all RH updates with timestamps

WRITE ACCESS: Only via RH Module interface

READ ACCESS: Available to all modules (read-only)

Work Order Collection (workOrders):

Add new field: completionRH (Number) - stores SNAPSHOT of RH at completion time

Add new field: completionRHValidated (Boolean) - indicates if RH passed validation

Add new field: completionRHSource (String) - where RH came from ("RH_MODULE", "MANUAL_ENTRY", "AUTO_FETCHED")

CRITICAL: This field NEVER writes back to RH Module

PURPOSE: Historical record only, for audit trail and trend analysis

B. RH Timeline History:

Create or ensure existence of a comprehensive RH history collection that logs every single RH update from any source:

javascript
Collection: rhTimeline
{
  _id: ObjectId,
  machineryId: String,           // e.g., "Main Engine - 702.005.02"
  machineryCode: String,          // Component code
  runningHours: Number,           // RH value at this point
  recordedDate: Date,             // Date this RH value was recorded for
  enteredDate: Date,              // Date this entry was created in system
  source: String,                 // "RH_MODULE", "WORK_ORDER", "MANUAL_ADJUSTMENT"
  sourceReference: String,        // Reference ID (work order ID if from WO, etc.)
  enteredBy: String,              // User who made the entry
  isValidated: Boolean,           // Whether this entry passed validation
  validationDetails: Object,      // Details of validation checks performed
  createdAt: Date,
  updatedAt: Date
}
This collection provides the complete chronological timeline needed for validation.

2. RH VALIDATION LOGIC:

When a crew member enters a Running Hours value while completing a work order, the system must perform comprehensive validation before accepting it.

VALIDATION ALGORITHM STEPS:

Step 1: Fetch the RH Timeline

Query the rhTimeline collection for the specific machinery

Get all RH entries sorted chronologically by recordedDate

Include entries from: RH Module, previous work orders, manual adjustments

Step 2: Identify the Time Window
For the completion date being entered (let's call it TARGET_DATE):

Find PREVIOUS_ENTRY: The most recent RH entry BEFORE target date

Find NEXT_ENTRY: The earliest RH entry AFTER target date (may not exist if target date is most recent)

Step 3: Calculate Valid Range

Backward Validation (against PREVIOUS_ENTRY):

text
Days between = TARGET_DATE - PREVIOUS_ENTRY.recordedDate
Max possible RH increase = Days between × 24 hours
Minimum valid RH = PREVIOUS_ENTRY.runningHours
Maximum valid RH (backward) = PREVIOUS_ENTRY.runningHours + (Days between × 24)
Forward Validation (against NEXT_ENTRY, if exists):

text
Days between = NEXT_ENTRY.recordedDate - TARGET_DATE
Max possible RH increase = Days between × 24 hours
Must satisfy: NEXT_ENTRY.runningHours - Entered RH ≤ (Days between × 24)
This gives us: Minimum valid RH (forward) = NEXT_ENTRY.runningHours - (Days between × 24)
Final Valid Range:

text
Minimum RH = Max(PREVIOUS_ENTRY.runningHours, NEXT_ENTRY.runningHours - days_to_next × 24)
Maximum RH = Min(PREVIOUS_ENTRY.runningHours + days_from_prev × 24, NEXT_ENTRY.runningHours)
Step 4: Check Basic Rules

Entered RH must be >= 0 (cannot be negative)

Entered RH must be > PREVIOUS_ENTRY.runningHours (RH cannot go backward)

If NEXT_ENTRY exists: Entered RH must be < NEXT_ENTRY.runningHours (cannot exceed future)

Entered RH must be within calculated valid range

Step 5: Additional Validation Checks

Check for Zero/Minimal Increase:
If entered RH equals previous RH (no increase), flag a warning:

"Warning: Running hours show no increase. Confirm machinery was not operated during this period."

Allow entry but mark for review

Check for High Utilization Rate:
Calculate average hours per day:

text
Average hrs/day = (Entered RH - PREVIOUS_ENTRY.runningHours) / Days between

If average hrs/day > 20:
  Flag as "HIGH_UTILIZATION" anomaly
  Show warning: "This indicates machinery ran 20+ hours per day. Please confirm."
  Require mandatory justification note before allowing save
3. DETAILED EXAMPLES FOR VALIDATION:

EXAMPLE 1: Valid Entry

text
RH Timeline for Main Engine (702.005.02):
  March 1, 2026  → RH = 500 hrs (from RH Module)
  March 11, 2026 → RH = 620 hrs (from RH Module, current)

Crew fills work order:
  Completion Date: March 6, 2026
  Entered RH: 560 hrs

VALIDATION:
  Previous entry: March 1 (500 hrs)
  Next entry: March 11 (620 hrs)
  
  Backward check:
    Days = March 6 - March 1 = 5 days
    Max increase = 5 × 24 = 120 hrs
    Entered increase = 560 - 500 = 60 hrs
    60 ≤ 120 ✅ VALID
  
  Forward check:
    Days = March 11 - March 6 = 5 days
    Max increase = 5 × 24 = 120 hrs
    Actual increase = 620 - 560 = 60 hrs
    60 ≤ 120 ✅ VALID
  
  Valid range: 500 to 620 (actually narrower: 500 to 620)
  Entered: 560 ✅ ACCEPT
  
  Average utilization = 60 hrs / 5 days = 12 hrs/day ✅ Normal
