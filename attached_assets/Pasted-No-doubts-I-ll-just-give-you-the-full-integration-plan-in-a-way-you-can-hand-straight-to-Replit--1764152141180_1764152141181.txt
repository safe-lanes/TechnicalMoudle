# MAINTENANCE PLANNER – INTEGRATION SPEC FOR PMS

## 1. WHAT IS THIS & WHAT ARE WE TRYING TO ACHIEVE?

### 1.1 Purpose

The **Maintenance Planner** is a consolidated planning screen that shows **upcoming and overdue maintenance jobs** across the vessel, with:

* Calendar-based jobs (due in next X days)
* Running-hours–based jobs (due in next X hours)
* Filters by **time window**, **remaining RH**, **rank**, **department**, **criticality**
* Export to **Excel/PDF** for planning meetings, office reporting, and wall charts

It is **not** a new maintenance engine; it is a **planning and visibility layer** on top of modules we already have:

* Components (equipment hierarchy)
* Jobs (maintenance templates per sub-component)
* Running Hours (parent components)
* Work Orders (execution + history)
* Spares (availability status)

### 1.2 High-Level Goals

1. Give CE/HOD a **single screen** to see:

   * What is **overdue**
   * What is **due soon**
   * What is **coming in the next 30/60/90 days**
   * What is **RH-based and approaching in the next 250/500/1000 hours**

2. Allow them to **filter by rank** and **workload**:

   * Example: “Show all jobs for Fitter in next 30 days”
   * Example: “Show all jobs for 3E in next 500 hours”

3. Let them **export** the filtered list into:

   * PDF (for print / ECR wall chart / email to office)
   * Excel (for further filtering, sharing, analysis)

4. Do this **without breaking existing rules**:

   * Part A of WO remains immutable
   * All structural changes still go via **Modify PMS**
   * RH logic (parent vs child) remains unchanged
   * Spares & criticality behave exactly as defined earlier

## 2. FROM WHERE WILL IT GET THE DATA? (DATA SOURCES)

The planner is a **read-only aggregation view** that pulls from existing tables/APIs.
Replit devs must NOT create new “planner-only” data tables for jobs; it should reuse existing PMS entities.

Below is the conceptual data map (names are indicative; adapt to your DB schema).

### 2.1 Jobs Data (Core)

**Source:** Vessel Jobs table (imported from Fleet Jobs + vessel Excel + Modify PMS)

Essential fields needed:

* `job_id`
* `job_code`
* `job_title`
* `component_id`
* `component_code`
* `component_name`
* `department` (Engine / Deck / Electrical)
* `assigned_rank` (Fitter / 4E / 3E / etc.)
* `job_type`

  * `CALENDAR`
  * `RUNNING_HOURS`
* `frequency_days` (nullable if RH-based)
* `frequency_hours` (nullable if calendar-based)
* `lead_time_days` (for calendar jobs; from Admin job settings)
* `lead_time_hours` (for RH jobs; from Admin job settings)
* `last_done_date`
* `last_done_rh` (for RH jobs)
* `critical_flag` (Y/N)
* `class_related_flag` (Y/N)
* `estimated_man_hours` (optional but useful)

> These should already exist in your Job table or can be derived from imports.

### 2.2 Running Hours Data (for RH jobs)

**Source:** Running Hours module (parent components)

Fields:

* `component_id` (parent)
* `current_rh`
* `last_rh_update_date`

For each **RH-based job**, we need to know:

```text
delta_rh = parent_component.current_rh - job.last_done_rh
remaining_hours = job.frequency_hours - delta_rh
```

> Remaining hours is the key field for RH filters like “next 250/500/1000 hours”.

### 2.3 Work Order Data (status & overdue logic)

**Source:** Work Orders module

We need, per job:

* Latest **open WO** for that job (if any):

  * `wo_id`
  * `wo_status` (DUE / OVERDUE / POSTPONED / COMPLETED / CANCELLED)
  * `wo_due_date` (for calendar jobs)
  * `wo_generated_date`
* Previous completed WOs (historical) – only to derive `last_done_date` / `last_done_rh` if not already stored in job.

The planner will **display status** based on combination of job + WO + dates/RH.

### 2.4 Component Data (context for grouping/filtering)

**Source:** Components module

Fields needed:

* `component_id`
* `component_code`
* `component_name`
* `sfi_code`
* `department`
* `location` (Engine Room, Pump Room, etc.)

Used for display and grouping, not for logic.

### 2.5 Spares Data (readiness indicator)

**Source:**

* Job–Spare mapping table (which spares are required for this job)
* Spares inventory table

For each job:

* Required spares (list of `part_code`)
* For each `part_code`:

  * `ROB_total`
  * `min_qty`
  * `critical_spare_flag`

From this we derive:

```text
spare_status:
  - OK       → All required spares ROB >= required & ROB >= min
  - LOW      → At least one spare ROB < min but > 0
  - ZERO     → At least one spare ROB = 0
  - NOT_SET  → No spares mapped
```

This shows as an icon/colour in planner.

### 2.6 User / Rank Data (filter)

**Source:** User master / Rank master

Needed to populate **rank filter** and correctly label `assigned_rank`.

## 3. HOW TO DO THE FUNCTIONALITY (BACKEND + FRONTEND)

### 3.1 Where in the PMS?

Create a new screen/module:

* **Route suggestion:** `/maintenance-planner`
* **Menu label:** `Maintenance Planner`
* Accessible under: **Work Orders / Planning** section.

Permissions:

* Read-only for all **Engine/Deck/Electrical officers**
* Same read-only view for Office with vessel dropdown

---

### 3.2 Core Backend Endpoint

Create a backend API something like:

`GET /api/v1/maintenance-planner`

**Query parameters:**

* `vessel_id` (required)
* `from_date` (for calendar jobs)
* `to_date`
* `remaining_hours_min` (for RH jobs)
* `remaining_hours_max`
* `job_type` (`CALENDAR`, `RH`, `BOTH`)
* `rank` (multi-select; optional)
* `department` (optional)
* `critical_only` (bool; optional)
* `include_overdue` (bool; optional; default = true)

Backend should:

1. Load all active jobs for the vessel.

2. Join with:

   * Running Hours (for RH jobs)
   * Work Orders (for current WO status)
   * Components (for name, dept, location)
   * Spares inventory & mapping (for spare_status)

3. Compute:

   * **For calendar jobs**:

     * `next_due_date` (existing field or derived from last done + frequency)
     * `status` (OVERDUE / DUE_SOON / FUTURE)
   * **For RH jobs**:

     * `remaining_hours` = `frequency_hours` – (`current_rh` – `last_done_rh`)
     * `status` based on remaining_hours thresholds

4. Apply filters:

   * Calendar:

     * Overdue: `next_due_date < today`
     * Filter window: `today <= next_due_date <= today + X days`
   * RH:

     * Show jobs where `remaining_hours <= threshold` (e.g., 250/500/1000)
     * “Overdue” when `remaining_hours <= 0`

5. Return **flat list** of jobs with all display data:

```jsonc
[
  {
    "job_id": "...",
    "job_code": "...",
    "job_title": "...",
    "job_type": "CALENDAR" | "RH",
    "component_code": "...",
    "component_name": "...",
    "department": "ENGINE",
    "assigned_rank": "Fitter",
    "critical_flag": true,
    "class_related_flag": false,
    "estimated_man_hours": 4,
    "next_due_date": "2025-12-05",        // for calendar jobs
    "remaining_hours": 180,               // for RH jobs
    "status": "OVERDUE" | "DUE_SOON" | "FUTURE",
    "wo_id": "WO-12345",                  // if WO already generated
    "wo_status": "DUE",
    "spare_status": "OK" | "LOW" | "ZERO" | "NOT_SET"
  },
  ...
]
```

### 3.3 Planner Filters (Frontend Behaviour)

Top filter bar should have:

1. **Job Type Filter**

   * Radio or dropdown:

     * `All`
     * `Calendar-based jobs`
     * `RH-based jobs`

2. **Date Window (for calendar jobs)**

   * Quick buttons:

     * `7 days`, `30 days`, `60 days`, `90 days`
   * Also allow custom date range (from–to date picker)

3. **Remaining Hours Window (for RH jobs)**

   * Quick buttons:

     * `<= 250 hrs`, `<= 500 hrs`, `<= 1000 hrs`
   * Also allow manual min/max RH input

4. **Status Filter**

   * `Overdue`
   * `Due Soon` (within chosen window)
   * `All`

5. **Rank Filter**

   * Multi-select dropdown of ranks (Fitter, 4E, 3E, ETO, Pumpman, etc.)

6. **Department Filter**

   * `Deck`, `Engine`, `Electrical`, `All`

7. **Criticality Filter**

   * Toggle or dropdown:

     * `All`
     * `Critical Only`

8. **Buttons**

   * `Apply` (if you don’t want auto-filter) OR instant filter on change
   * `Reset Filters`

### 3.5 Actions / Functional Hooks

1. **View Job Details**

   * Opens a modal with:

     * Full job description
     * Procedure
     * Tools & spares list
     * Job history (last few WOs)

2. **View Component**

   * Navigates to Components module, selected component.

3. **View Work Order**

   * If `wo_id` exists:

     * Opens WO screen with that WO pre-loaded.

4. **Generate WO** (for jobs with no currently open WO)

   * Calls existing backend endpoint to:

     * Create a WO using that job’s Part A data
     * With due date = job’s calculated next due date (for calendar)
     * For RH jobs, due immediately (status “Due”)
   * After success, planner refreshes WO status column.

5. **Postpone** (For authorised users)

   * Opens existing “Postpone WO” modal
   * Writes to WO history and job history as already defined in your system.
   * Planner then fetches updated due date/status.

> NOTE: This module should **reuse existing APIs**: “create WO”, “postpone WO”, “get job”, “get component”.
> New logic required only for **aggregation & filtering**.

Two endpoints or one endpoint with format parameter.

**Backend:**

`GET /api/v1/maintenance-planner/export?format=excel`
`GET /api/v1/maintenance-planner/export?format=pdf`

* They accept the **same filters** as the UI (or reuse the already-filtered dataset sent from frontend).
* Export **only filtered results**.

**Excel Export:**

Columns:

* Component Name

Two layout styles can be supported (either now or later):

1. **Detailed list** (same data as table).

---

### 3.8 Permissions & Safety Rules

* **No change** to Component RH logic.
* Planner **never** writes directly to:

  * Job frequency
  * Last done date / RH
  * Component structure
* Any structural change must still go via **Modify PMS**.
* Planner only triggers:

  * WO creation (using existing logic)
  * WO postpone (using existing logic)
  * Navigation/view actions
* Planner reads only **active jobs** (ignore inactive/obsolete).
