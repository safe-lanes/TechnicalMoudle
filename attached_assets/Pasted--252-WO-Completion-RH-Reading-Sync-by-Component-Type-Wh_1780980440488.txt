#252 - WO Completion — RH Reading Sync by Component Type
What & Why
When a technician completes a Running Hours (RH) based Work Order, they enter a Current Reading in Section B3 of the WO form. Today this reading is validated against the RH module's stored value and hard-blocked if the entered value is higher — even when the machinery has legitimately run more hours since the last RH module update.
This forces a two-step duplicate workflow:
Go to RH module → update manually
Come back to WO form → enter the same value again
The fix introduces component-type-aware behaviour at WO completion:
MASTER component WO → Current Reading updates the RH module (MASTER updated, delta cascades to all INHERITED children automatically)
INHERITED component WO → Current Reading is stored on the WO only, used to calculate the next RH cycle. The RH module is intentionally not touched.
NOT_RH_DRIVEN component WO → No change. Existing behaviour preserved.
Logic & Examples
Rule 1 — MASTER Component
Formula:
If WO component = MASTER:  validate: enteredRH > previousReading  (must be monotonic)  validate: (enteredRH − currentMasterRH) ≤ (daysSinceLastUpdate × 25 hrs)  if validation passes → complete WO + update MASTER RH → cascade to all INHERITED  if daily cap exceeded → require admin override to proceed
Example:
MASTER (Main Engine)       → RH module: 5,000 hrs  (last updated 3 days ago)INHERITED A (Turbocharger) → RH module: 5,000 hrs  (cached from MASTER)INHERITED B (Fuel Pump)    → RH module: 5,000 hrs  (cached from MASTER)WO raised for MASTER (Main Engine). Tech enters Current Reading = 5,180.Validation:  increase = 5,180 − 5,000 = 180 hrs  days since last RH update = 3  max allowed = 3 × 25 = 75 hrs  180 > 75 → FAILS daily cap → admin override requiredIf Sail Admin overrides and confirms:  WO completes  RH module: MASTER → 5,180  Cascade fires:    INHERITED A (Turbocharger) → 5,180  ✅    INHERITED B (Fuel Pump)    → 5,180  ✅  job_component_links (Main Engine):    lastDoneRH = 5,180    nextDueRH  = 5,180 + interval  Audit log: source = 'workorder_completion'If increase was within cap (e.g., 5,060 → increase 60 hrs over 3 days):  Proceeds without override. Same cascade outcome.
Rule 2 — INHERITED Component
Formula:
If WO component = INHERITED:  validate: enteredRH > previousReading  (must be monotonic, cannot go backwards)  no daily rate cap check (not writing to RH module)  if validation passes → complete WO    → store completionRH on WO record    → update job_component_links: lastDoneRH = enteredRH    → calculate nextDueRH = enteredRH + intervalRunningHour    → RH module NOT updated (intentional)
Example:
MASTER (Main Engine)         → RH module: 5,000 hrsINHERITED A (Turbocharger)   → RH module: 5,000 hrs (cached)INHERITED B (Fuel Pump)      → RH module: 5,000 hrs (cached)WO raised for INHERITED A (Turbocharger). Interval = 2,000 hrs.Tech enters Current Reading = 5,200.Validation:  5,200 > previousReading (5,000)?  YES → PASS ✅  (No daily rate cap check — not writing to RH module)WO completes:  WO record: completionRH = 5,200  job_component_links (Turbocharger):    lastDoneRH = 5,200    nextDueRH  = 5,200 + 2,000 = 7,200  ✅  RH module:   unchanged ← intentional  MASTER:      still 5,000  INHERITED B: still 5,000Next WO for Turbocharger:  Generated when component RH reaches 7,200 − 720 = 6,480  ✅Later: MASTER updated to 5,300 via RH module (cascade fires):  INHERITED A cached value → 5,300  INHERITED B cached value → 5,300  job_component_links.nextDueRH for Turbocharger → still 7,200 (unaffected) ✅
Why INHERITED does not update the RH module: The MASTER is the single source of truth for all shared running hours. If an INHERITED WO pushed a reading to the MASTER, it would overwrite the MASTER's actual counter — which may be ahead of or behind the completion reading — and cascade that incorrect value to every other INHERITED component on the same engine. The completion reading is only meaningful for that specific component's maintenance cycle, not for the engine's total runtime counter.
Rule 3 — NOT_RH_DRIVEN Component
No change. No RH validation. No RH update. Existing behaviour preserved.
Guard — Double-Sync Prevention
If a MASTER WO is reopened and completed a second time with a different reading, the RH module must not receive a second push that conflicts with the first.
Rule: Once a MASTER WO has successfully synced its reading to the RH module, flag the WO with rhSyncedAt (timestamp). On any subsequent completion attempt, skip the RH module update. The audit log retains the original sync entry.
Guard — Same-Day Block
If the RH module was already updated today for the MASTER component:
The daily cap validation fires (daysSinceLastUpdate = 0 → block)
Only a Sail Admin override can proceed
Error message shown in WO form: "RH already updated today. Admin override required."
Done Looks Like
Tech completes a MASTER component WO, enters 5,060 hrs → RH module auto-updates to 5,060, all INHERITED children cascade to 5,060. No separate RH module visit needed.
Tech completes an INHERITED component WO, enters 5,200 hrs → WO completes, next due RH calculated as 7,200. RH module shows no change. No error shown.
If MASTER reading increase exceeds 25 hrs/day cap, the WO form shows a clear message and requires a Sail Admin to confirm before proceeding.
Re-completing a MASTER WO after an initial sync does not push a second RH update.
Audit log in the RH module shows a new entry with source = 'workorder_completion' whenever a MASTER WO completion triggers an RH update.
All INHERITED WO completions continue to calculate next cycle correctly, independent of whatever the RH module currently shows.
Out of Scope
Changing how the RH module's manual update flow works (unchanged)
Changing how the cascade propagation works (existing updateMasterRH() used as-is)
Dual Frequency jobs (RH leg follows the same MASTER/INHERITED split logic; Calendar leg is unchanged — handle as a follow-up if needed)
Bulk import or sync paths for RH (unchanged)
Any UI redesign of the RH module itself
Steps
Split the ceiling block by component type — In the WO completion validation path, replace the single hard block (runningHours > componentActualRH) with a three-way branch on rhCounterType. MASTER: apply daily-rate validation (25 hrs/day cap) instead of the hard ceiling. INHERITED: apply monotonic check only (entered ≥ previousReading). NOT_RH_DRIVEN: skip entirely.
Trigger MASTER RH update on completion — After a successful WO completion for a MASTER component, call the existing updateMasterRH() service with the completion reading. This fires the full cascade to all INHERITED children automatically. Write audit entry with source: 'workorder_completion'.
Add double-sync guard — Add a rhSyncedAt timestamp field to the work orders table (new migration). On WO completion, check this flag before triggering the RH module update. If already set, skip the update silently. Set the flag on first successful sync.
Surface admin override in WO form — When the daily rate cap is exceeded for a MASTER component, the WO form must show a clear inline warning with the calculated allowed range and provide a Sail Admin override confirmation step before allowing the completion to proceed.
Smart suggestion in WO form (B3) — When user opens B3 on an RH-based WO, display a read-only hint showing: last known RH, last updated date, and the valid entry range (lastRH to lastRH + one interval). For MASTER: also show the 25 hrs/day cap ceiling. No estimated projection — only the factual range.
Verify next-cycle calculation for INHERITED — Confirm that job_component_links.lastDoneRH and nextDueRH are written correctly from the completion reading for INHERITED WOs (this already exists today — step is a verification pass with a targeted test, not new code).
