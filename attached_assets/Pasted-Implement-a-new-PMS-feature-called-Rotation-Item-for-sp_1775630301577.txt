Implement a new PMS feature called “Rotation Item” for spares. This feature is required for spare parts that are used on a rotation basis, where one set is fitted onboard and another set may go ashore for reconditioning, overhaul, servicing, or exchange.

The implementation must be done in a way that the new field is available and visible in all relevant spare-related screens, especially:

Spares module main listing and filters.

Spare Details popup in the Spares module.

Components sub-module, Section E “Spares”.

Functional objective
Add a new boolean field named Rotation Item for each spare record. This field must indicate whether the spare is managed as a rotational spare or not.

The business meaning is:

Rotation Item = Yes: the spare belongs to a rotation-based set and may be alternated with another set, including cases where one set is sent ashore for reconditioning/repair/service.

Rotation Item = No: the spare is a normal spare and not handled under rotation logic.

For this phase, only implement the field, visibility, editing control, display, and filtering behavior. Do not introduce any separate reconditioning workflow, exchange cycle tracking, or rotation history unless already present elsewhere.

Data model changes
Add a new field to the spare master data:

Field name: is_rotation_item

Type: boolean

Default value for existing and new records: false / No.

Also ensure:

The field is returned in all spare-related APIs used by the Spares listing, spare detail popup, and Component Section E spare list.

The field is accepted in create and update payloads for spare records.

Export logic should include this new field wherever spare master data export already exists in the Spares module.

UI changes in Spares module
1. Spares listing table
In the Spares module inventory listing, add a new column called Rotation Item.

Column behavior:

Show value as a small status tag, chip, or plain text: “Yes” or “No”.

Keep styling consistent with existing tags like stock/criticality/IHM style language used in the product.

Place the new column in a logical position near spare classification fields. Recommended placement:

after “Criticality” and before “ROB”, or

near the existing part-identification columns if that matches your table layout better.

2. Spares filters
Add a new filter for Rotation Item in the Spares module filters area.

Filter requirements:

Label: Rotation Item

Type: dropdown/select

Options:

All

Rotation Items

Non-Rotation Items

Filter behavior:

All = no filtering on this field.

Rotation Items = show only spare records where is_rotation_item = true.

Non-Rotation Items = show only spare records where is_rotation_item = false.

Ensure this filter works correctly together with existing filters such as stock and other active list filters. Filter combinations must be additive and not override each other unexpectedly.

3. Add/Edit Spare form
Wherever spare master data is created or edited in the Spares module, add a new field:

Label: Rotation Item

Control type: toggle switch preferred; checkbox acceptable only if the product uses checkboxes elsewhere for booleans.

Behavior:

Off = No

On = Yes

Default = Off for new records.

Add the field in a logical place under basic classification/stock identity fields, without disturbing the form flow.

Spare Details popup changes
In the Spare Details popup, add a visible field for Rotation Item in the Basic Information section or another logically suitable section of the popup. The current popup already displays key identification and stock fields, so this new field should appear there as a first-class attribute, not hidden in notes or a secondary area.

Display requirements:

Show as a toggle-style field or read-only toggle-style indicator.

Clearly show Yes/No state.

Edit permissions in popup:

Sail Admin: editable in view mode.

Client Admin: editable in view mode.

Head of Department: visible but disabled/greyed out in view mode.

Vessel view mode users: visible but disabled/greyed out.

Important:

The field must be visible to all these roles in the details popup.

For roles without edit rights, the toggle must look disabled but still readable.

Do not hide the field for read-only roles.

If the popup currently supports inline edit in view mode for selected roles, extend the same pattern to this field. If the popup is fully read-only and only certain admins can modify specific fields inline, then implement Rotation Item under the same inline-edit convention.

Components sub-module changes
In Components sub-module, Section E “Spares”, add one more column called Rotation Item. The current Section E table already shows part code, part name, component, part number, critical, ROB, min, stock, location, IHM, and actions, so this must be added to that table.

Column behavior:

Show Yes/No or a compact visual tag.

Keep alignment and widths consistent so the Actions column remains visible and usable.

Do not break the current table layout or cause horizontal overlap in normal desktop resolution.

Also add an editable control for Rotation Item at Section E level if the row interaction already supports spare editing or detail opening from this section. If direct inline edit is not supported in Section E, then at minimum:

show the column value in the list,

ensure the spare detail view opened from there also exposes the same Rotation Item toggle with correct permission behavior.

Permission matrix
Implement the following strict permission rules for Rotation Item:

Role	Visibility	Editability
Sail Admin	Visible	Editable
Client Admin	Visible	Editable
Head of Department	Visible	Disabled / greyed out
Vessel view mode	Visible	Disabled / greyed out
This applies specifically to:

Spare Details popup.

Any spare form or inline spare view where this field is shown.

If role logic is already centralized in frontend and backend, extend that existing authorization model rather than hardcoding UI-only checks. Also enforce update permission on the backend API so non-authorized roles cannot update the field via direct request manipulation.

API and backend behavior
Update backend spare APIs so that:

spare detail responses include is_rotation_item,

spare list responses include is_rotation_item,

create/update endpoints accept and persist is_rotation_item,

unauthorized roles receive proper rejection on update attempts.

Validation rules:

Accept only boolean true/false.

If field is missing in old records or old payloads, treat as false.

Backward compatibility must be maintained for existing records and older UI flows.

Display standards
Use consistent naming across all screens:

Label: Rotation Item

Display value conventions:

Toggle ON = Yes

Toggle OFF = No

In tables, show “Yes” / “No” or equivalent compact badge.

Greyed-out state requirements:

For Head of Department and Vessel view mode, the control must be clearly disabled but still legible.

Do not reduce contrast so much that it becomes unreadable.

Tooltip optional: “Read only” or “No permission to edit” if your design system supports it.

UX consistency requirements
Maintain consistency with the current PMS UI:

Same spacing, label style, field typography, and card layout as existing spare details popup.

Same filter styling and dropdown behavior as current Spares module filters like Criticality and Stock.

Same table styling in Components Section E and Spares listing.

Do not introduce a different toggle component style from the rest of the application. Reuse the existing toggle/switch component if available.

Migration and existing data
For existing spare records:

set Rotation Item to No by default.

Add database migration for this field and ensure no existing listing, popup, or export breaks because of null values. Use safe fallback handling for older data.

Testing requirements
Please test the following scenarios thoroughly:

Existing spare records load successfully with Rotation Item defaulted to No.

New spare can be created with Rotation Item = Yes.

Sail Admin can edit Rotation Item from the spare detail view.

Client Admin can edit Rotation Item from the spare detail view.

Head of Department can see Rotation Item but cannot change it; control is greyed out.

Vessel view mode user can see Rotation Item but cannot change it; control is greyed out.

Spares module filter “Rotation Items” returns only records with Yes.

Spares module filter “Non-Rotation Items” returns only records with No.

Combined filters still work correctly with stock and other existing filters.

Components Section E shows the Rotation Item column correctly.

Spare detail popup displays the same Rotation Item value consistently wherever opened from.

Unauthorized API update attempts are blocked at backend level.

Acceptance criteria
The feature will be considered complete only if all of the following are done:

Rotation Item field exists in spare master data.

Rotation Item is visible in Spares module listing.

Rotation Item filter exists and works.

Rotation Item is shown in Spare Details popup.

Rotation Item appears in Components sub-module Section E as an additional column.

Sail Admin and Client Admin can edit it.

Head of Department and Vessel view mode can only view it in disabled state.

Backend, API, UI, and permission logic are all aligned.

Implementation note
This must be treated as an enhancement to the existing spare master and spare visibility flow, not as a separate new module. Keep the implementation minimal, clean, and fully integrated into current PMS screens and role-based access behavior.
