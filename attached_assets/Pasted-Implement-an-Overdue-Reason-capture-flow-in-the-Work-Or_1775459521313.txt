Implement an “Overdue Reason” capture flow in the Work Orders module, modeled on the existing Postponement Reason pattern.

Objective
In the Overdue tab of the Work Orders (W.O) page, add a new reason capture action in the Status column. When the user clicks it, open a popup showing:

A dropdown of predefined overdue reasons (coming from a new master list: “Overdue Reason List”)

An “Other Reason” option in the dropdown

A free-text box that becomes mandatory when “Other Reason” is selected and optional otherwise

A Save button that stores the overdue reason and optional remarks on the work order

This feature must not interfere with the existing computed status logic (Planned/Due/Overdue etc. remain purely output).
​

Functional requirements
New action in Overdue tab

In WorkOrders.tsx, in the Overdue tab view, add an icon/button or clickable label in the Status column (e.g., “Set Overdue Reason” or an edit icon within the status cell).

The action should be visible only when:

effectiveStatus === 'Overdue', and

The work order does not yet have an overdue reason (or you can show it as an edit action if a reason already exists, depending on current patterns).

Clicking this action opens an “Overdue Reason” modal dialog.

Overdue Reason modal UI

The modal should follow the same style system as the existing Postpone Work Order popup.
​
​

Fields:

Dropdown: Overdue Reason* (required)

Options populated from Master Lists (see below).

Include an extra option “Other Reason”.

Text area: Remarks / Additional Details

Optional when a standard reason is selected.

Mandatory when “Other Reason” is selected.

Placeholder behavior:

Standard reason: “Enter additional remarks or details…”

Other Reason: “Enter custom overdue reason…”

Buttons:

Cancel (closes modal, no changes)

Save (validates and persists)

Validation

Dropdown selection is always required.

If selected value is “Other Reason”:

The text area must be non-empty after trimming.

On empty, show a clear validation message (e.g., “Please enter the custom overdue reason”) and do not submit.

If a standard reason is selected:

Text area is optional.

Data model / persistence

Add or reuse fields on the work order record (confirm existing schema before creating new columns):

overdueReason (string) – stores the selected master-list value or “Other Reason”.

overdueReasonDetails (string) – stores the free-text remarks / custom reason.

Behavior:

When user saves:

If standard reason:

overdueReason = selected value (e.g., “Crew workload / manpower limitation”)

overdueReasonDetails = optional remarks

If “Other Reason”:

overdueReason = “Other Reason”

overdueReasonDetails = user-entered text (actual reason text)

Do not change status or any computed status fields. Overdue still comes only from computedStatus.
​

Expose these fields in the Work Orders API DTO so the frontend can:

Decide whether to show “Set Reason” or “Edit Reason”

Display existing overdue reason in detail view or tooltip

Master Lists – Overdue Reason List
New list type

In MasterListsManagement.tsx (or equivalent), add a new list type entry:

ts
{ value: 'overdueReason', label: 'Overdue Reason' }
This should appear in the same dropdown where Department / Rank / Interval Unit / Component Category / Location / Postpone Reason are configured.
​

Master list behavior

Master Lists UI for Overdue Reason should behave exactly like other list types:

Table showing Key / Value / Display Order / Active / Actions

Add New, Edit, Delete (as per current rules)

Active toggle, with only active entries offered in UI

Seeding initial values

In initDb (or equivalent seeding logic), add an idempotent seed for Overdue Reason entries, following the same pattern used for postponementReason:

Insert default overdue reasons into master_lists with list_type = 'overdueReason'.

Use ON CONFLICT (list_type, list_key) DO NOTHING so admin changes are preserved.

You can start with a small, reasonable default set, for example:

Crew workload / manpower limitation

Waiting for spares or consumables

Operational priority / equipment in continuous use

Weather / sea conditions

Port operations / cargo operations

Permit / isolation / access constraints

(plus any others already aligned with postponement reasons)

Actual list text can be adjusted to match operational standards; the critical part is that values are master-list driven.

API usage

Reuse the existing Master List API endpoint:

text
GET /technical/api/fleet/master-lists?listType=overdueReason
Overdue Reason modal must:

Fetch options via this endpoint (active items, ordered by displayOrder).

Append “Other Reason” on the client side (unless you decide to store it as an always-active static entry in the master list).

Handle loading and error states similarly to the Postponement Reason dialog:

Disable dropdown while loading

On error, show message and optionally allow a fallback (but still require at least “Other Reason”).

Frontend implementation details
Overdue Reason modal component

Create a new component, e.g. OverdueReasonDialog.tsx, modeled on PostponeWorkOrderDialog.tsx:

Props: workOrder, open, onClose, onSaved.

Uses React Query (useQuery) to load master list options for listType=overdueReason.

Uses a mutation (useMutation) to call a backend endpoint to save overdueReason and overdueReasonDetails for the given work order ID.

WorkOrders.tsx integration

In the Overdue tab rendering, add an action in the Status column:

If wo.overdueReason is empty: show a subtle “Set Reason” pill/button.

If present: show an icon or label like “Reason set” (clickable to edit).

On click, open OverdueReasonDialog with the selected work order.

After save, refetch or optimistic-update that row so the UI reflects that a reason is now set.

Backend endpoint

Add a new endpoint, e.g.:

text
POST /technical/api/fleet/work-orders/:id/overdue-reason
Request body:

json
{
  "overdueReason": "Crew workload / manpower limitation",
  "overdueReasonDetails": "Only 2 E/R crew on watch at that time"
}
Validation:

overdueReason required, trimmed non-empty.

If overdueReason === 'Other Reason', overdueReasonDetails must be non-empty after trim.

This endpoint must NOT modify status or computed fields; it only writes the reason fields.

Reporting / usage
Overdue reasons should be:

Visible in the work order detail view (for audit).

Available to exports / reports in the same way postponement reasons are.

It is not required in this task to add filters by overdue reason, but the data model should make that easy later.

Acceptance criteria
New Overdue Reason entry exists in Master Lists and works with Add/Edit/Delete/Active toggle.

Overdue tab status column shows a reason action for overdue work orders.

Clicking the action opens an Overdue Reason modal with:

Master-list-driven dropdown values

“Other Reason” option

Textarea behaving as optional vs mandatory as per rules.

Save persists overdueReason and overdueReasonDetails for the work order via API.

Existing status computation and tab behavior remain unchanged (tabs still driven only by computedStatus).
​

User can revisit a work order and see/edit the stored overdue reason.

No regression to the existing Postpone Work Order flow or Master Lists Management UI
