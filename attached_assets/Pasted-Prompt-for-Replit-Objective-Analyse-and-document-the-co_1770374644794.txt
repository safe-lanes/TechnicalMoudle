Prompt for Replit
Objective:
Analyse and document the complete backend data model, APIs, workflows, and business logic used for report generation in the PMS system.
The output must be provided in a single, well-structured .md file.
Instructions
You must NOT modify any code. This task is analysis and documentation only.
Prepare a markdown document that clearly explains how report data is produced end-to-end.
Scope of Analysis
1. Backend Tables Used for Reports
Provide a complete list of all backend tables involved directly or indirectly in report generation.
For each table, document:
Table purpose (why it exists)
All columns with:
Column name
Data type
Description / business meaning
Primary key
Logical uniqueness rules (e.g. vessel-wise uniqueness)
Whether the table is:
Master data
Transactional
Derived / audit / history
⚠️ Highlight tables where:
Data is duplicated
JSON columns are used instead of relational structure
Vessel-wise isolation is expected but not enforced
2. APIs Used for Report Generation
List all APIs used to fetch data for reports.
For each API:
Endpoint path
HTTP method
Input parameters (especially vessel-related filters)
Tables queried
Join logic (high-level explanation)
Filters applied (date, status, vessel, component, job, etc.)
Whether the API supports:
Single vessel
Multi-vessel
Fleet-wide data
Clearly mention APIs that:
Mix data across vessels unintentionally
Depend on cached or derived data
Use incorrect or incomplete filters
3. Report Data Workflow (End-to-End)
Explain the complete workflow of report generation:
Where report data originates (source tables)
How transactional data is accumulated (jobs, work orders, running hours, spares, stores, defects, etc.)
How updates (bulk upload / single edit) affect report data
How historical data is preserved (or not)
At what point data becomes eligible for reports
Include simple flow diagrams in text form, for example:
Work Order Completion
 → Running Hours Update → History/Audit Entry
 → Report Query Fetch 
4. Business Logic Used in Reports
Document the core logic rules, including:
Next due calculations
Running hours calculations
Status derivation (OVERDUE / DUE_SOON / FUTURE)
Job frequency and scheduling logic
Spare consumption & ROB calculations
Store balance calculations
For each logic:
Where it is implemented (API / service / query)
Which columns are used
Any known inconsistencies or assumptions
5. Vessel-Wise Data Handling
Explicitly analyse and document:
How vessel_id is applied across tables
Where vessel filtering is missing or incorrect
Which reports assume vessel isolation but don’t enforce it
Which APIs default to a single vessel unintentionally
6. Gaps Affecting Report Accuracy
Identify and list:
Missing tracking tables
Missing audit/history records
Incorrect column usage (e.g. wrong date fields)
Data overwritten instead of versioned
Logic that depends on frontend state instead of persisted data
Explain how each gap impacts report correctness.
7. Summary for Report Stability
End the document with:
Key risks in current report generation
Tables or APIs most responsible for inconsistencies
Areas that must be fixed before reports can be considered reliable
Output Requirements
Single .md file
Clear headings and subheadings
No code changes
No assumptions without explanation
Focus on how reports are generated today, not how they should be built
