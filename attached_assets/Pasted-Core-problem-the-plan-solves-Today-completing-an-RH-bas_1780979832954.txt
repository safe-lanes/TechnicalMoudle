Core problem the plan solves
Today, completing an RH-based Work Order runs a single hard block: if the technician's entered Current Reading (Section B3) exceeds the component's stored RH value, completion is rejected and they're told to go update the RH module first (server/services/workOrderService.ts:280-291 — runningHours > componentActualRH → throw). That forces a duplicate two-step dance (update RH module → re-enter the same value on the WO). The requirement is to replace that one-size-fits-all ceiling with behaviour that depends on the component's RH counter type, so a legitimately-higher reading at completion is accepted and routed correctly.

The pivot point: component rhCounterType
The whole design keys off the existing enum MASTER | INHERITED | NOT_RH_DRIVEN (confirmed shared/schema.ts:261, 355). Each component already carries rhCounterType, plus rhMasterComponentId (INHERITED → its MASTER), an actual-RH field for MASTER, and a cached-RH field for INHERITED. The plan branches completion validation three ways:

1. MASTER component WO — the reading is authoritative for the engine's real counter.

Validate monotonic (entered > previous) and a daily-rate cap: (entered − currentMasterRH) ≤ daysSinceLastUpdate × 25 hrs.
On pass: complete the WO, then call the existing updateMasterRH() (confirmed at runningHours/services/runningHoursService.ts:585) which cascades the new value to all INHERITED children automatically — write an audit entry with source: 'workorder_completion'.
If the cap is exceeded (including same-day, where daysSinceLastUpdate = 0 → always blocks) → require a Sail Admin override to proceed.
2. INHERITED component WO — the reading matters only for that component's maintenance cycle, not the engine counter.

Validate monotonic only (no rate cap, because nothing is written to the RH module).
On pass: store completionRH on the WO, write job_component_links.lastDoneRH = entered and nextDueRH = entered + interval (those columns exist: shared/schema.ts:3070-3071), and deliberately do not touch the RH module.
The rationale I take as a hard design constraint: the MASTER is the single source of truth; pushing an INHERITED completion reading up to the MASTER would corrupt the shared counter and cascade a wrong value to every sibling.
3. NOT_RH_DRIVEN WO — untouched, no RH validation/update.

Two guards (both about protecting the MASTER counter)
Double-sync guard: a new rhSyncedAt timestamp on work_orders (confirmed it does not exist yet → needs a new migration). Once a MASTER WO has synced, set the flag; any re-completion skips the RH push so reopening a WO can't overwrite the counter twice. The original audit entry stays.
Same-day block: falls out of the daily-cap formula (0 days → 0 allowed), surfaced as "RH already updated today. Admin override required."
UI expectations
B3 smart hint (read-only, factual only — no projections): last known RH, last updated date, valid range (lastRH … lastRH + interval); for MASTER also show the 25 hrs/day ceiling.
Inline admin-override step in the WO form when a MASTER reading breaches the cap, showing the calculated allowed range before letting a Sail Admin confirm.
Scope boundaries I noted
Unchanged: RH module's manual update flow, the cascade mechanism itself (updateMasterRH() reused as-is), bulk import/sync RH paths, and any RH-module UI redesign. Dual-Frequency jobs are explicitly a follow-up (RH leg would follow the same split; calendar leg untouched). The INHERITED next-cycle step is a verification pass with a test, not new logic.

Risks / ambiguities I'd want resolved before building
Grounding the plan in code surfaced a few things the plan doesn't fully pin down:

Duplicate workOrderService.ts files. The hard block is in server/services/workOrderService.ts, but there's also server/modules/work-orders/services/workOrderService.ts and a workOrderCompletionService.ts. Per the project's own "duplicate files / confirm the live code path" rule, the first step must confirm which service actually runs at completion so the branch isn't added to dead code.

A second, parallel hard ceiling exists. The RH module's own path (running-hours/controllers/runningHoursController.ts:235 + rhTimelineValidationService.ts) has its own "exceeds actual running hours" / backward / future-conflict checks. The plan targets the WO-completion path only — but if MASTER completion routes through updateMasterRH(), we need to be sure those RH-side validations don't re-block the very reading we just accepted.

The 25 hrs/day cap is a magic constant — where it lives (per-vessel/component config vs hardcoded) and whether it's already defined anywhere isn't specified.

"Sail Admin override" enforcement is described at the UI layer; the server completion path also needs to accept and authorize an override flag (role check), otherwise the cap is bypassable or unenforced server-side.

rhSyncedAt migration must follow this repo's strict workflow (db:generate, the required audit columns, idempotency) — not db:push.
