Your plan is directionally correct, but it is still too loose and leaves room for implementation mistakes. The page is already unstable, and we cannot accept a design that is “mostly right” but error-prone. The final implementation must be robust, deterministic, and based on a proper vessel-specific node-instance model, not a loosely adapted version of the current flat org chart logic.

1. Do not treat rank master rows as org chart nodes
The Ranks Admin table remains the global rank master only. The vessel org chart must be built using vessel-specific node instances that reference rank master records but store their own configuration. This is mandatory because the same rank can appear multiple times in one vessel setup, and each occurrence must behave independently.

2. Do not rely on rankId uniqueness in the org chart
A rank such as Oiler, Motorman, or any other role may appear multiple times in the same vessel hierarchy. Therefore, the org chart data model must use a unique node instance ID as the primary identity, while rankId is only a reference to the master rank. No save, update, drag-drop, or preview logic should assume one node per rank ID.

3. Separate master label from vessel node label
The master rank label and the vessel node label must not be treated as the same field. The vessel org chart must allow node-level label override, because repeated positions may use the same rank but need different labels for clarity in that vessel structure. Editing the label in vessel org chart must not overwrite the global rank master label.

4. Unassigned Ranks must not be a one-time exhausted source list
The Unassigned panel must not behave as “show ranks that are unused once and disappear forever after drag.” It must support creation and management of multiple vessel node instances derived from the same master rank. If you keep a simple left-side source list without instance creation logic, repeated rank usage will fail in practice.

5. Removal must mean unassign, not delete
The default behavior for removing a node from hierarchy must be to return it to the Unassigned Ranks pool. It must not be permanently deleted by default. Deletion, if supported at all, must be an explicit separate action and clearly distinguished from unassignment.

6. The structure must be department-first, not one free-form tree
The vessel org chart must be built in this order:

Department block

One HOD within that department

Subordinate nodes under that HOD or under valid child nodes in that same department

Do not implement this as one global unrestricted tree with department as a side attribute. The editing experience must be clearly department-wise because this structure will later support department ownership and work order approval routing.
7. HOD must be a node-level business flag

HOD is not to be inferred automatically from rank name such as Master, Chief Officer, or Chief Engineer. The user must explicitly mark one node in each department as HOD. The system must store this as a node-level business attribute.
8. Preview must be driven by saved hierarchy data, not temporary UI state

The live org chart preview must render directly from the same underlying hierarchy data that will be saved and reloaded. Do not maintain a separate visual-only model for the preview, because that creates sync issues and future bugs.
9. Department data and view mode data must come from existing system sources

Department options must come from the existing Department Master source. View mode options must reuse the existing application values already used by the ranks module, such as SAIL Admin, Client Admin, Head of Dept, Vessel, Superintendent, etc. Do not introduce disconnected hardcoded lists unless absolutely unavoidable.
10. Save and reload must be exact and lossless

Saving must persist all vessel-node attributes exactly, including:

vessel reference

node instance ID

rank reference

vessel-specific label

department

parent node

HOD flag

assigned/unassigned status

view mode

sort order

Reloading must reconstruct the exact same hierarchy and preview without loss of structure or metadata.
11. First-time vessel setup must be deterministic

If a vessel has no existing org chart configuration, the screen must load in a clean first-time state with:

empty department blocks,

available rank source / instance creation path,

unassigned rank area,

no broken tree state,

no null-reference errors,

no dependency on pre-existing old modal org chart data.
12. Do not partially retrofit the old modal logic

The old org chart appears to be a simple modal tree view. Do not stretch that design beyond its limits. If needed, create a dedicated vessel org chart configuration layer and migrate old data carefully, but do not carry forward structural weaknesses from the previous flat implementation.
13. Error tolerance is mandatory

We cannot accept a feature that works only in ideal demo conditions. The implementation must be stable when:

a vessel has no configuration,

the same rank appears multiple times,

some nodes remain unassigned,

department HOD is not yet marked,

labels are edited,

nodes are moved repeatedly between departments and unassigned area,

the page is refreshed mid-work after saving.
14. Acceptance must be based on business behavior, not visual completion

This feature is not complete just because drag-and-drop and a preview render on screen. It is complete only if the underlying saved hierarchy can be reliably reused later for department management and approval workflow logic.
15. Build for future workflow use now

This org chart is a business configuration layer, not a decorative chart. Build it now so that future work order approval routing can consume department ownership, HOD selection, parent-child reporting line, and view mode without redesigning the module later.
