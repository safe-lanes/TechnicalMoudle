# ✅ IMPLEMENTATION BRIEF — PMS Dashboard (Compliance + Interactive)

## Goals

Upgrade the **Dashboard** screen to a modern, interactive, compliance-ready view that pulls **only from our existing data** (Components, Work Orders, Running Hrs, Spares/Stores, Certificates, Defects, Modify PMS). No new modules or breaking UI; reuse our current styles (cards, badges, table fonts, colors) and routing.

---

## 0) Global Layout & Controls (top of dashboard)

* Add a sticky control bar at top:

  * **Vessel selector** (dropdown, default “All Vessels”) → same source as vessel filters used elsewhere.
  * **Time range** (Month to date | Last 30 days | Quarter | Custom).
  * **Filters** (Dept: Deck/Engine/Electrical | Critical Only toggle).
* All tiles/charts below must **react** to these controls.

---

## 1) KPI Header Tiles (row of cards)

Make 6 compact cards, responsive 3×2 on desktop, 2×3 on tablet.

1. **Total Components**

   * Count = components for selected vessel(s)
   * Small subtext: Δ vs previous period (green up or red down).

2. **Active Work Orders**

   * Count where status ∈ {Pending, In Progress}.

3. **Overdue Tasks**

   * Count where due date < today and status ≠ Completed.
   * Small red subtext: “+X this week”.

4. **Completed This Period**

   * Count of WOs completed in selected time range.
   * Subtext: “+X% vs last period”.

5. **Critical PMS Compliance** (NEW compliance tile)

   * % of **critical** PMS tasks due this period that were **completed on time**.
   * Show % + small badge: Green (≥95%), Amber (90–94%), Red (<90%).

6. **Fleet Compliance Index** (office users only; hide onboard if single vessel)

   * % PMS compliance across all visible vessels this period.
   * Badge coloring same as above.

Data mapping (use current back-end/collections):

* Components: `components` table
* Work orders: `work_orders` with fields `status`, `due_date`, `completed_date`, `is_critical` (or from linked component)
* Period comparisons: compute client-side with same dataset (no new endpoints).

---

## 2) Work Orders Status (stacked bars list)

Card with 4 rows, each as a colored band (compact):

* **Pending**, **In Progress**, **Completed**, **Overdue** (overdue row in red).
* Each row shows count; clicking opens Work Orders list page **pre-filtered** (vessel, status, time range).

---

## 3) Upcoming Maintenance (inspection-friendly)

Small list with 4 lines:

* **Next 7 days** — count of due WOs
* **Next 30 days** — count
* **Critical** — count of due or due-within-period critical WOs
* **Routine** — rest
  Click → opens filtered Work Orders.

---

## 4) Inventory Overview (Spares & Stores)

Two mini cards side-by-side:

* **Spares**: count of items + a tiny red link “X Low Stock” (ROB < Min).
* **Stores**: same logic.
  Click → jump to respective modules, pre-filtered by low stock & vessel.

---

## 5) Certificates & Compliance (new block)

* **Certificates Due**: counts due in 30 / 60 / 90 days (three small numbers).
* **IHM Status**: small pill showing “Compliant / Attention / Unknown”:

  * Compliant = % of IHM-flagged components with required docs attached ≥ 95%
  * Attention = 80–94%
  * Unknown < 80% or missing flags
* **LSA/FFA test summary** (if available in WOs): last test date vs due date with green/amber/red dot.

All link to the relevant list pages with filters applied.

---

## 6) Reschedule / Change Requests (Modify PMS integration)

Add a small card:

* **Change Requests**: Pending Approval, Approved this period, Rejected this period.
* **Postponed PMS Jobs**: number this period + top 3 reasons (chips: spares, voyage, manpower).
  Click → opens Modify PMS filtered.

---

## 7) Visuals — Modern, Interactive Charts

### 7.1 Maintenance Heatmap (calendar grid)

* Weekly/daily grid for the selected period.
* Color intensity = number of due tasks that day.
* Toggle chips above heatmap: **All | Critical Only | Deck | Engine | Electrical**.
* Hover shows tooltip with counts; click drills to WO list for that day.

### 7.2 Recurring Issues Trend (defects)

* Line + bar combo: last 6 months

  * Bars: defects opened by month
  * Line: % closed within 30 days
* Right legend: Top 5 categories (count + small sparkline).
  Click → opens Defects filtered.

(Use existing Defects module data. If defect categories are absent, use tag/keyword buckets we already store; do **not** invent new schema.)

---

## 8) Quick Actions (shortcuts)

Row of 4 compact buttons:

* **Create Work Order** → new WO form
* **Update Running Hours** → running hrs screen
* **Add Component** → component add/edit
* **Generate Report** → reports module (preselect PMS summary report)

Keep same icons & button style as existing app.

---

## 9) System Status (right column)

* Database: Online/Degraded (green/amber)
* Backup: Updated (timestamp of last backup)
* Sync Status (for offline clients if applicable): Synced/Out-of-sync
* Last Update: “X min ago”
  Pull from our existing health/heartbeat endpoints if present; if not, hide gracefully.

---

## 10) Drill-downs & Routing

All tiles/charts must be **clickable** and route to the correct module **with filters pre-applied**:

* Respect vessel, time range, and any categorical filter used in the widget.
* Use existing list screens; **do not** build new pages.

---

## 11) Performance & UX

* Skeleton loaders for each card/chart.
* Responsive: 2-column layout collapses to 1-column on <1200px.
* No blocking calls; load cards in parallel.
* Reuse our existing color tokens:

  * Success/OK green, Warning amber, Danger red, PMS blue accents.
* Keep typography and card shadows consistent with current app.

---

## 12) Acceptance Criteria

* All numbers/graphs change when **vessel** or **time range** changes.
* **No new tables/endpoints** created; only existing data sources are read.
* All drill-downs land in the correct module with filters applied.
* Overdue vs Grace (due within period but not yet overdue) are clearly distinguished.
* Critical PMS Compliance and Fleet Compliance Index badges color correctly:

  * Green ≥95%, Amber 90–94%, Red <90%.
* Low-stock counts match Spares/Stores module logic (ROB < Min).
* No layout shifts: lighthouse CLS < 0.1 on desktop.

---

## Data Source Mapping (use existing fields)

* **Work Orders**: `id, vessel_id, status, due_date, completed_date, department, is_critical, frequency_type, frequency_value`
* **Components**: `id, vessel_id, category, department, criticality`
* **Running Hrs**: `component_id, current_rh, updated_at`
* **Inventory (Spares/Stores)**: `item_id, type, rob, min, vessel_id`
* **Certificates**: `id, type, due_date, vessel_id`
* **Defects**: `id, opened_at, closed_at, category, vessel_id`
* **Change Requests (Modify PMS)**: `id, status, reason, created_at, approved_at`

If a field name differs in our code, **map to the equivalent already used in that module**—do not alter schema.

---

## Don’ts

* Do **not** introduce new menu items, schemas, or visual theme.
* Do **not** add third-party chart libs if we already use one; otherwise use a lightweight lib consistent with our bundle.
* Do **not** hardcode numbers; everything must be live from our data.

---

If any existing endpoint is missing a filter (e.g., vessel or date range), implement the filter **in the client** after fetching (paged) data, or ask before changing backend. Keep changes isolated to the Dashboard module.
