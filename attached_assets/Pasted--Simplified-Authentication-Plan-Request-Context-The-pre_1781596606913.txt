# Simplified Authentication Plan Request

## Context

The previously proposed solution introduces full JWT signature verification on the backend. While that is the correct long-term security solution, it carries significant implementation and deployment risk:

* Requires confirming JWT algorithm (HS256/RS256/etc.)
* Requires matching JWT secrets with the parent portal
* Requires validating JWT claim mappings
* May break existing integrations, sync services, or background jobs
* Risk of locking all users out if secrets/configuration are incorrect
* Requires backend authentication middleware changes across the application

For now, we want a much smaller and lower-risk first step.

## Objective

Implement only a basic session-presence check on the frontend.

We are NOT implementing backend JWT verification at this stage.

The goal is simply to prevent users from directly opening PMS URLs when no authenticated session exists in local storage.

## Desired Behaviour

### Scenario 1 - Valid Session Exists

1. Read the `credentials` value from local storage.
2. Decrypt it using the existing `secureGetItem("credentials")` logic.
3. If a non-empty token/value is successfully retrieved:

   * Treat the user as authenticated.
   * Allow navigation to PMS routes.
   * Existing application behaviour should continue.

### Scenario 2 - No Session Exists

If:

* `credentials` key is missing, OR
* decryption fails, OR
* decrypted value is empty/null,

then:

* User should be considered unauthenticated.
* Any attempt to access PMS routes directly should redirect to `/login`.
* PMS pages should not render.

Example:

```text
https://dev.sl-sail.com/pms/workorders
```

with no credentials stored should become:

```text
https://dev.sl-sail.com/login
```

### Scenario 3 - Logout

On logout:

* Clear credentials from storage.
* Redirect to `/login`.
* Refreshing the page must not automatically restore Sail Admin access.

## Important

Do NOT implement:

* JWT signature verification
* Backend authentication middleware
* JWT secret configuration
* Role validation
* Token expiry validation
* Permission enforcement

This phase is only intended to remove the automatic Sail Admin fallback and ensure PMS routes require the presence of a stored credential.

## Deliverables

Please first analyse the existing authentication flow and produce an implementation plan covering:

1. Files that need modification.
2. How AuthContext currently hydrates the user.
3. How DEFAULT_USER fallback currently works.
4. How route guarding should be implemented.
5. How `/login` should behave.
6. How logout should be updated.
7. Any impact on existing development workflows.

Do not implement immediately. First provide the detailed plan and impact assessment for review.
