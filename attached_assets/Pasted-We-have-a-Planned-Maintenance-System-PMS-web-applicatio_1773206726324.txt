We have a Planned Maintenance System (PMS) web application. Work orders (WOs) have already been implemented with the following features from previous layers:

Layer 1: missedCycles is calculated for each WO and displayed as an orange badge on the WO list

Layer 2: Next Due Date is auto-calculated from completion date (cannot be manually changed)

Layer 3: Work History (A4 section) records every completion with date, performed by, description, status, remarks

Layer 4B: When missedCycles >= 1, the CE must type a justification in a "CE Justification for Skipped Cycles" field before approving. This field is stored in the database.

Each work order has these relevant fields already in the database:

dueDate — the original due date of the WO

completionDate — the date the crew entered as the completion date in Part B

missedCycles — integer, pre-calculated (how many cycles were skipped)

status — can be: planned, due, overdue, pending_approval, completed

ceJustification — text field (from Layer 4B)

approvedBy — who approved

approvedAt — when approved

WHAT YOU NEED TO IMPLEMENT — LAYER 5: APPROVAL WORKFLOW HARDENING

This layer adds tiered approval logic based on how many days late the completion is, and also handles the skipped cycles case. Read every requirement carefully.

STEP 1 — ADD NEW DATABASE FIELDS

Add the following new fields to the work order model/schema (wherever WO data is stored — check existing schema files):

text

  — calculated as: completionDate minus dueDate in days. If completionDate <= dueDate, daysLate = 0.

STEP 2 — ADD TIER CALCULATION LOGIC

Create a function (call it calculateApprovalTier) that must be called AUTOMATICALLY whenever a work order is submitted for approval (i.e., when status changes to pending_approval).

This function calculates daysLate and sets approvalTier according to these exact rules:

text
Rule 1 — missedCycles >= 1 (skipped cycles detected):
  → approvalTier = "superintendent_locked"
  → This OVERRIDES all other rules. Even if daysLate is only 2, if missedCycles >= 1, it is superintendent_locked.
  → superintendentAcknowledged must be false (reset it)
  → Set superintendentNotifiedAt = current timestamp

Rule 2 — missedCycles == 0 AND daysLate > 14:
  → approvalTier = "superintendent_notification"
  → superintendentNotifiedAt = current timestamp
  → superintendentAcknowledged = false

Rule 3 — missedCycles == 0 AND daysLate >= 7 AND daysLate <= 14:
  → approvalTier = "ce_with_justification"

Rule 4 — missedCycles == 0 AND daysLate >= 0 AND daysLate < 7:
  → approvalTier = "standard"
Store daysLate and approvalTier in the database when this function runs.

STEP 3 — APPROVAL GATE LOGIC (BACKEND)

In the API endpoint that handles WO approval (the endpoint where CE clicks "Approve"), add the following blocking logic BEFORE allowing the approval to go through:

text
Check A — If approvalTier == "superintendent_locked":
  → BLOCK approval completely
  → Return error: "This work order has skipped cycles detected. It is locked pending Superintendent acknowledgment. The CE cannot approve until the Superintendent has acknowledged."
  → The WO status must remain "pending_approval" — do NOT change it

Check B — If approvalTier == "superintendent_notification":
  → DO NOT block CE approval
  → But REQUIRE ceApprovalRemarks to be non-empty (minimum 20 characters)
  → If ceApprovalRemarks is empty or less than 20 characters, return error: "This completion is more than 14 days late. You must enter detailed remarks (minimum 20 characters) before approving."
  → After CE approves: set status = "completed", log approval, AND trigger superintendent notification (see Step 5)

Check C — If approvalTier == "ce_with_justification":
  → REQUIRE ceApprovalRemarks to be non-empty (minimum 10 characters)
  → If ceApprovalRemarks is empty or too short, return error: "This completion is 7–14 days late. Approval remarks are mandatory."
  → After CE approves: set status = "completed", log approval normally

Check D — If approvalTier == "standard":
  → No extra requirements. CE can approve normally (ceApprovalRemarks optional)
  → After CE approves: set status = "completed"
STEP 4 — SUPERINTENDENT ACKNOWLEDGE ENDPOINT

Create a new API endpoint:

text
POST /api/work-orders/:id/superintendent-acknowledge
This endpoint:

Checks that approvalTier == "superintendent_locked" on the WO — if not, return error "This WO does not require Superintendent acknowledgment"

Sets superintendentAcknowledged = true

Sets superintendentAcknowledgedAt = current timestamp

Sets approvalTier = "ce_with_justification" — IMPORTANT: after Superintendent acknowledges, the WO is NOT immediately approved. It drops down to the next tier so the CE must still approve with mandatory remarks.

Does NOT change the WO status — it remains "pending_approval" so CE still needs to approve

Returns success with message: "Superintendent has acknowledged. The Chief Engineer can now approve with mandatory remarks."
