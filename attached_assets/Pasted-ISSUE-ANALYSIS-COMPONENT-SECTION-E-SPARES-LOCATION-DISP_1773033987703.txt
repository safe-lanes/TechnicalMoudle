ISSUE ANALYSIS – COMPONENT SECTION → E. SPARES (LOCATION DISPLAY)

Context:
In the Component section under "E. Spares" (Highlighted Area), the system is displaying 3 spare locations along with ROB values.

However, when verifying in the Spares master data, only 2 location columns exist:
• Location A
• Location B

Problem:
The UI is displaying a 3rd location even though only two locations are defined in the spares table.

Points to Investigate:

1. Data Source Verification
   - Check from which table the spare location data is being fetched.
   - Confirm whether the UI is pulling data from:
     a) Current Spares table
     b) Spare transaction/history table
     c) Stock movement table
     d) Any cached or aggregated data source.

2. History Data Influence
   - Verify if the third location is being fetched from historical spare transactions.
   - If historical data exists for an old location, confirm why it is still appearing in the component E. Spares view.

3. Business Logic Validation
   - The system should display only the currently active spare locations defined in the Spares master.
   - Old or historical locations should not appear in the Component view unless explicitly required.

4. Query / API Logic Review
   - Inspect the backend query used to fetch spare locations.
   - Check whether the query is incorrectly joining with history or transaction tables.

5. UI Rendering Logic
   - Verify if the UI is dynamically generating location columns based on historical records instead of the master location fields.

Expected Behaviour:
The Component → E. Spares section should display only the active locations defined in the Spares master table (Location A and Location B).

Correction Method:

1. Restrict the data source to the current spare master table.
2. Exclude historical or transaction-based locations from the display.
3. Ensure the UI renders only the defined location columns.
4. Validate that ROB values correspond strictly to Location A and Location B.

Deliverables:
• Root cause of the third location display
• Corrected backend query logic
• UI adjustment if required
• Confirmation that only two locations will be displayed moving forward.
