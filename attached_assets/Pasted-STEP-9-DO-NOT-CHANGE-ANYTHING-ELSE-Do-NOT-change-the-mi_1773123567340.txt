EDGE CASES TO HANDLE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Handle these carefully in your code:

1. originalDueDate is null or undefined:
   → Fall back to completionDate as the base (old behavior)
   → Log a warning in the server console: 
     "WARNING: originalDueDate missing for WO [id], 
      falling back to completionDate for next due calculation"

2. originalDueDate is in the future (job completed early):
   → This is fine. Still use originalDueDate as base.
   → nextDue = originalDueDate + interval (which will be in the future,
     correct behavior)

3. frequencyUnit is "Months" or "Years":
   → Use date-fns addMonths() or addYears() functions
   → Do NOT use a fixed number of days for months/years 
     (months have different day counts)

4. The work order has no associated job record (edge case):
   → Fall back to completionDate + interval (old behavior)
   → Log a warning in the server console

5. Multiple completions of the same job over time:
   → Each completion uses THAT WO's nextDueDate as originalDueDate
   → The chain self-corrects: each new WO is created with the 
     correct nextDueDate = previousOriginalDueDate + interval
   → The schedule always stays anchored to the original planned dates
