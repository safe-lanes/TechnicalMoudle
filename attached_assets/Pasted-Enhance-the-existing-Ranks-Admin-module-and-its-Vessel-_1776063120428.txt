Enhance the existing Ranks Admin module and its Vessel Org Chart functionality into a full vessel-specific hierarchy management feature. Do not create a disconnected new module. This must be implemented as part of the current admin flow where ranks are already maintained.

The current page already has the following context and data available in the rank master list: ranks such as Master, Chief Officer, Second Officer, Chief Engineer, Bosun, Pumpman, Fitter, Motorman, Chief Cook, Messman, etc., and columns for Rank ID, Name, Label, Category, and View Mode. This existing rank data must be treated as the source for the org chart setup.

Main objective
Build a vessel-specific department hierarchy configuration tool that allows the user to organize crew rank nodes into a structured vessel org chart. This structure will later be used for department management and future work order approval routing, so the implementation must store real hierarchy relationships and not just visual chart positions.

The UI must support:

assigning rank nodes to department blocks,

selecting one Head of Department (HOD) per department,

drag-and-drop hierarchy arrangement,

assigning View Mode for each node,

maintaining unassigned ranks separately,

and showing a live org chart preview that updates when the hierarchy changes.

Scope and constraints
This feature must be vessel-specific.

Do not implement copy-from-other-vessel or template-copy functionality now; however, keep the data model and screen flow flexible so that copy functionality can be added later without redesigning the module.

Do not implement advanced validations now beyond basic structural usability; strict business validation can be added later.

Do not replace the existing Ranks Admin purpose; instead, extend it so that rank master data remains the base source and the vessel org chart becomes a vessel-level configuration layer built from that source.

Functional concept
The org chart should not be treated as one flat visual tree. It should be managed in this logical order:

Department block

One HOD node inside that department

Other rank nodes placed under the HOD or under subordinate parent nodes within the same department

This means the user should first be able to assign ranks to departments, then place them inside department sections, then define parent-child hierarchy within the department.

Important business rules
The implementation must respect these business rules:

Each vessel will have its own org chart configuration.

The source of available crew roles comes from the existing rank master records visible in the Ranks Admin page.

A rank can appear more than once in a vessel structure, because repeated roles may exist for the same vessel; when repeated, the labels can differ, so each placed rank must be treated as a separate configurable node instance, not as one shared row.

Every node in the hierarchy can have only one parent.

Each department can have only one HOD.

Department assignment must be selectable directly in the org chart configuration screen using the existing Department Master / master lists as the source for available departments.

Unassigned ranks must remain visible in a dedicated section outside the org chart and must be draggable into the hierarchy later if needed.

Nodes not placed into the chart should not disappear from the user’s control; they must remain available in the Unassigned Ranks list/table.

The View Mode options already exist in the system, such as SAIL Admin, Client Admin, Head of Dept, Vessel, Superintendent, etc.; these must be reused from the existing application logic and not recreated as a disconnected hardcoded list unless absolutely necessary.

Screen design requirement
Implement the feature using Option C, meaning the screen must combine both editing controls and a live visual preview.

The screen should be divided into three clearly distinguishable working areas:

Area 1: Unassigned Ranks

Area 2: Department-wise editable hierarchy builder

Area 3: Live org chart preview

These areas may be arranged side-by-side on large screens and stacked logically on smaller screens, but all three must remain part of the same workflow.

Area 1: Unassigned Ranks
This section must display all rank node instances that are available for the selected vessel but are not currently placed into any department hierarchy.

Expected behavior:

Show rank name, label, and basic identification details for each unassigned item.

Allow drag-and-drop from Unassigned Ranks into a department block or hierarchy area.

If a node is removed from the hierarchy, it should return to Unassigned Ranks instead of being deleted immediately.

Unassigned Ranks should behave like a staging area or pool of available crew positions for the vessel.

This section is important because your requirement says that disabled or not-yet-used ranks should remain outside the org chart but still visible and available for future assignment.

Area 2: Department-wise editable hierarchy builder
This is the core working area where the user configures the vessel organization.

The hierarchy builder must:

show department blocks based on department master data,

allow rank nodes to be assigned into department blocks,

allow drag-and-drop reordering and nesting of nodes,

allow one node in each department to be marked as HOD,

allow node movement back to Unassigned Ranks,

allow editing of node attributes such as label, department, HOD flag, and view mode.

Department block behavior
Each department block should act as a container for nodes belonging to that department.

Expected department block behavior:

The department header should clearly identify the department name from master data.

Users should be able to drop rank nodes into that department.

A department can contain one HOD and multiple subordinate nodes.

The HOD does not have to be system-derived automatically; instead, the user must be able to explicitly mark one node as HOD inside the department.

If a department has nodes but no HOD yet, the UI should still allow configuration, but it should clearly show that HOD has not been assigned yet.

Node behavior
Each placed node should represent one vessel-specific rank instance.

Each node should visually display at minimum:

Rank name

Label

Department

HOD status

View mode

Assignment status

Each node should support these actions:

drag to reorder within the same department,

drag under another node to make that node the parent,

drag back to Unassigned Ranks,

mark/unmark as HOD,

change department if moved or edited,

change view mode from dropdown,

edit label if your current app supports label distinction for repeated roles.

Parent-child behavior
The hierarchy builder must store actual parent-child relationships.

Expected parent-child logic:

A node can have only one parent.

When dragged under another node, the parent relationship must update in the underlying data.

The UI should make it visually clear which node reports to which parent.

A node without a parent but inside a department should be interpreted as top-level within that department unless marked as HOD.

HOD should normally sit at the top of the department block, but the tool should still be flexible enough to reorder nodes visually while preserving the HOD role as a business attribute.

Area 3: Live org chart preview
The preview must not be a static mockup. It must be a live visual representation of the actual configured hierarchy.

Expected behavior:

As soon as the user drags, reorders, assigns department, marks HOD, or changes view mode, the preview should refresh immediately.

The preview should present the structure in a readable org chart format grouped by department.

Each department should be visually separated.

The HOD should appear clearly at the top of that department’s chart section.

Subordinate nodes should appear below based on the current parent-child structure.

Unassigned nodes should not appear in the final org chart preview, because they are outside the chart until assigned.

View Mode requirement
The current ranks table already includes a View Mode column, which means this concept already exists in the module. In the vessel org chart enhancement, every node instance shown in the hierarchy builder must have a visible View Mode dropdown in front of it or on the node row/card itself.

Expected behavior:

View Mode must be configurable per vessel-specific node instance, not just per rank master record.

Existing system view mode values such as SAIL Admin, Client Admin, Head of Dept, Vessel, Superintendent, etc. must be reused from the application’s current source of truth.

The selected view mode must be saved as part of the org chart configuration.

The live org chart preview may optionally display the selected view mode as metadata if useful, but the main requirement is that it must be editable and persisted.

Relationship between rank master and vessel org chart
This distinction is extremely important and must be respected in the implementation.

Ranks Admin master list remains the system-wide rank definition source.

Vessel Org Chart becomes a vessel-level configuration built from that source.

The org chart must not directly corrupt or replace the global rank master definitions.

Vessel configuration should store rank instances referencing rank master records, while adding vessel-specific properties such as department, parent, HOD flag, assigned/unassigned status, and view mode.

This separation is required because you will later use the org chart for workflow and approvals, while still maintaining a clean master data model.

Data requirement in plain English
Even if the implementation is UI-first, the data must be stored in a structured form that supports future approval logic.

Each org chart node should conceptually store:

vessel reference,

unique node reference,

rank reference from rank master,

displayed label,

assigned department,

parent node reference,

HOD flag,

assigned or unassigned status,

view mode,

sort/reorder position.

The org chart should be saved as relationship data, not only as screen coordinates or drawing lines.

Save and load behavior
The feature must support proper persistence, not temporary visual editing.

Expected save/load behavior:

When a vessel is selected or opened, the page should load that vessel’s org chart configuration if it already exists.

If no configuration exists yet, the screen should initialize with rank nodes available in Unassigned Ranks and empty department blocks ready for assignment.

The user should be able to make changes and save them.

On refresh or reopening, the exact hierarchy must reload correctly, including department assignment, parent-child relationships, HOD flags, labels, assignment status, sort order, and view mode.

The preview must be generated from the saved hierarchy data, not from temporary UI state only.

Behavior for repeated ranks
Since the same rank can appear multiple times in a vessel, the implementation must not assume one row per rank only.

Expected behavior:

Each repeated position must behave as its own node instance.

The label should help distinguish repeated roles when needed.

Dragging one repeated node must not automatically move all other nodes with the same rank ID.

Saving one repeated node’s parent or view mode must not overwrite another repeated node’s settings.

Deletion and removal behavior
The user should not lose track of ranks because of destructive actions.

Expected behavior:

Removing a node from the org chart should return it to the Unassigned Ranks section, not permanently delete it immediately.

Permanent deletion of vessel node instances, if supported at all, should be a separate explicit action and not the default drag-out behavior.

Future-readiness requirement
This feature is being built now for department management, but it must be designed in a way that later supports:

work order approval routing,

department-wise approval ownership,

HOD-based approval logic,

copy org chart from another vessel or template,

stronger validation such as one HOD per department, prevention of circular hierarchy, mandatory parent rules, and required department mapping.

Because of this, the implementation must prioritize structured hierarchy data and maintain clean separation between global master data and vessel-specific configuration.

Acceptance criteria
The feature should be considered complete only if all of the following are true:

The user can open Vessel Org Chart from the existing Ranks Admin flow.

The screen shows Unassigned Ranks, editable department-wise hierarchy, and live org chart preview together in one working experience.

Rank master records from the current page are available as source input for the vessel org chart.

The user can drag a rank node from Unassigned into a department block.

The user can drag a node under another node to form hierarchy.

The user can mark exactly one node as HOD within a department.

The user can assign or change department for a node.

The user can set view mode for each node using the existing system options.

Unassigned nodes remain visible outside the chart and can be reused later.

The same rank can exist in multiple node instances without conflict.

Saving preserves the full configuration and reloading restores it accurately.

The org chart preview reflects the actual saved structure rather than a fake static diagram.

What not to do
To avoid wrong implementation, explicitly do not do the following:

Do not build only a visual chart without storing hierarchy relationships.

Do not overwrite the global rank master table with vessel-specific hierarchy data.

Do not hide unused ranks completely; keep them in Unassigned Ranks.

Do not restrict the design to one instance per rank master row.

Do not make HOD hardcoded by rank name; the user must mark the node as HOD inside the department.

Do not create a disconnected new page flow if this can be integrated cleanly into the existing Ranks Admin / Vessel Org Chart experience.
