V2 Modular Architecture Planning with Toggle-Based Backward Compatibility
Objective

Analyze the existing backend and frontend architecture and produce a clear, step-by-step migration plan to introduce a V2 module-wise RESTful architecture, starting only with:

Component Bulk Upload → Component Module (fetch & usage)

⚠️ This is a planning and analysis task only
❌ Do not write or modify any code
❌ Do not change any existing behavior
❌ Do not redesign or reimplement business logic

IMPORTANT:
The V2 architecture must use 100% the same business rules, validations, calculations, and workflows as legacy.
This initiative is purely an architectural re-organization, not a functional rewrite.

🔒 Backward Compatibility & Toggle Requirement (CRITICAL)

The current (legacy) architecture must remain fully intact

All new architecture must exist strictly under a /v2 namespace

No existing routes, services, schemas, logic, or UI behavior may break

V2 must behave identically to legacy for the same inputs

Frontend Toggle Rule

A frontend toggle (V2 / Switch to Legacy) will control behavior at runtime:

Enable or disable V2 routing dynamically

Decide whether data is fetched from:

Legacy APIs (current structure), OR

V2 APIs (/technical/api/api/v2/...)

The plan must clearly explain:

How the toggle determines API selection

How legacy and V2 run in parallel using the same logic

How rollback to legacy happens instantly, with zero data loss and no behavior difference

🔍 Scope of Work (STRICT)

Only the following flow is in scope:

Component Bulk Upload

Component Module consumption (fetch & usage)

The plan must introduce and align the following layers without modifying any legacy code paths or logic:

Mandatory Folder Structure

Repository Layer Rules

Service Layer Rules

Controller Layer Rules

RESTful Route Patterns

Frontend API Layer Rules

Critical Enforcement Rules

1️⃣ Mandatory Folder Structure (V2 ONLY)
Backend (per module)
server/v2/{module}/
├── index.ts
├── routes.ts
├── controllers/
│   ├── index.ts
│   └── {entity}Controller.ts
├── services/
│   ├── index.ts
│   └── {entity}Service.ts
└── repositories/
    ├── index.ts
    └── {entity}Repository.ts

Shared Schema & Types
shared/v2/{module}/
├── schema.ts
└── types.ts

Frontend (per module)
client/src/modules/{module}/
├── components/
├── hooks/
└── api/{module}ApiV2.ts


The plan must explicitly explain:

How existing legacy logic is reused or mirrored, not rewritten

How V2 services call the same logical steps as legacy

How architecture changes without changing outcomes

4️⃣ Repository Layer Rules

Only layer allowed to access the database

ORM query builders only

❌ No N+1 queries (must use JOINs)

❌ No business logic

Queries must produce the same data shape as legacy

5️⃣ Service Layer Rules

All existing business logic lives here unchanged

❌ No HTTP objects

❌ No database access

Handles audit user exactly as legacy

Applies create/update rules identically to legacy

6️⃣ Controller Layer Rules

HTTP concerns only

Schema validation only

Calls services only

❌ No ORM usage

❌ No business logic

Must behave exactly like legacy controllers

7️⃣ RESTful Route Patterns (V2 ONLY)
GET    /api/v2/{module}/{entity}
GET    /api/v2/{module}/{entity}/:uuid
POST   /api/v2/{module}/{entity}
PATCH  /api/v2/{module}/{entity}/:uuid
DELETE /api/v2/{module}/{entity}/:uuid   (soft delete)


Nested routes must follow proper hierarchy

Route responses must match legacy response contracts

🌐 Mandatory API Prefix (Nginx Rule)

All V2 frontend API calls must start with:

/technical/api/


This is mandatory to:

Separate PMS and Crew traffic

Support Nginx routing rules

Avoid legacy route collision

8️⃣ Frontend API Layer Rules (V2)

One API file per module

Toggle decides Legacy vs V2

Always pass auditUserUuid

❌ No direct fetch calls in components

Hooks/components consume module API only

UI behavior must remain unchanged

9️⃣ Critical Enforcement Rules

❌ No JSON columns

❌ No cross-module coupling

❌ No DB access outside repositories

❌ No functional or logical changes

❌ No data model behavior change

❌ No legacy code modification

🎯 Expected Output

Provide:

A phased migration plan (architecture-only)

Toggle-based flow diagram (Legacy ↔ V2)

Component Bulk Upload refactor plan (logic preserved)

Identified risk points with rollback strategy

Validation checklist proving:

Same inputs

Same logic

Same outputs
