Step 3 – Intermediary Approval Tracking Table

This is the key part of your proposal.

Instead of modifying the change_request table heavily, create an intermediary approval-tracking table.

Example:

Field	Purpose
id	PK
uuid	Unique ID
changeRequestUuid	Link to change_request
approvalLevel	Level 1 / Level 2
approverUserId	Assigned approver
status	Pending / Approved / Rejected
approvedAt	Timestamp
remarks	Approval remarks
createdAt	Timestamp

This table becomes the workflow engine.

For example:

Level 1 + Level 2 Configured

CR	Level	Status
CR001	Level 1	Pending
CR001	Level 2	Pending

After Level 1 approval:

CR	Level	Status
CR001	Level 1	Approved
CR001	Level 2	Pending

After Level 2 approval:

CR	Level	Status
CR001	Level 1	Approved
CR001	Level 2	Approved

This is cleaner than storing multiple approval columns in change_request.

Step 4 – Change Request Status

Your proposal:

Till the moment all required configured stages are completed, the Change Request should show as Pending Stage.

This is correct.

Suggested status flow:

Status	Meaning
Draft	Created but not submitted
Submitted	Request submitted
Pending Approval	Waiting for one or more approval stages
Approved	All configured stages completed
Rejected	Rejected at any stage
Synced	Approved and synchronized

For user visibility:

Level 1 pending → Pending Approval
Level 2 pending → Pending Approval

The actual stage can be derived from the intermediary table.

Step 6 – Rejection Logic

If any configured approval stage rejects:

Change Request
↓
Rejected
↓

↓
