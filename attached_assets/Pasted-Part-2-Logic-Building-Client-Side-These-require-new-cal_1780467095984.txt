Part 2 — Logic Building (Client Side)
These require new calculated behaviour and flow changes but stay in the frontend.

2a. Auto-calculate Duration and Next Due Date from Postpone Date
When the user picks a Postpone Date:

Postponement Duration (days) = Postpone Date − Original Due Date
Next Due Date                = Postpone Date  (they are the same value — the new target date)

Both fields update automatically as the user changes the date picker. If Postpone Date is before Original Due Date, show a validation error.

2b. Approver field — must be a real user dropdown
Currently "Authorized By" is a hardcoded dropdown (superintendent / technical-manager / dpa). The new Approver field must be populated from the vessel's actual office users or ranks — fetched from an existing /api/users or /api/ranks endpoint. This needs:

A useQuery to fetch eligible approvers
Validation that the field is required before submission
2c. Submission no longer immediately postpones
In WorkOrders.tsx → handlePostponeConfirm (currently line 923), the call sets status: "Postponed" directly. This changes to:

Call a new endpoint: POST /work-orders/:id/postpone-request
The WO moves to the Postponed tab but displays status "Awaiting Office Approval"
No date changes are applied to the WO yet
2d. Edit and Resubmit from the Postponed tab
When a WO has status "Awaiting Office Approval" or "Postponement Rejected":

The Postpone button (or a new Edit button) on the Postponed tab reopens the dialog pre-filled with the existing request data
On submit, it calls a different endpoint (resubmit) that creates a new audit entry while retaining history
The status resets to "Awaiting Office Approval"
2e. Rejection auto-reverts status on the UI
When a postponement is rejected, the WO must disappear from the Postponed tab and reappear in the Due or Overdue tab. This means the Postponed tab filter must exclude "Postponement Rejected" WOs (or the backend handles the status revert — see backend section).

2f. Office Dashboard — Pending Approval tab filter
In Dashboard.tsx, the pendingApprovalWOs filter currently shows WOs where computedStatus === 'Pending Approval' (this is the completion approval flow — vessel HOD/superintendent approval before close-out).

The new rule:

Show WOs with status "Awaiting Office Approval" (postponement requests)
Do NOT show WOs awaiting vessel-side HOD approval (existing superintendent_locked / approvalTier records — those are completion approvals, not postponement approvals)
This requires filtering the two types apart in the query result.

2g. Approve / Reject action in the Office Dashboard
In the Pending Approval grid, each "Postponement Approval Request" row needs an action button that:

Opens a detail panel (not a full new page — uses the existing layout) showing all postponement fields
Provides Approve and Reject buttons
Requires an Approval/Rejection Remarks text field (optional for approve, required for reject — or consistent either way)
Part 3 — Backend Changes
These require schema changes, new routes, and service logic.

3a. Schema changes — work_order_postponements table
The table already exists with most fields. Add the missing columns:

New Column	Type	Purpose
approver	TEXT	Name/ID of the approver selected by vessel user
approvalRemarks	TEXT	Remarks entered by office when approving/rejecting
postponeDate	TEXT	The specific date the vessel requested (= new due date)
durationDays	INTEGER	Already exists — auto-calculated and stored
Migration: npm run db:generate → review SQL → server applies on restart.

3b. Schema changes — work_orders table
The status field (line 1133 of schema) currently has: Active | Due | Due (Grace P) | Overdue | Postponed | Pending Approval | Completed. Add three new status values to the comment (the column is unconstrained text so no ALTER needed, but the comment and constants need updating):

Awaiting Office Approval
Postponement Approved
Postponement Rejected
Also add two new columns to work_orders for the current active postponement request:

New Column	Type	Purpose
postponeApprover	TEXT	Selected approver for the pending request
postponementApprovalDate	TEXT	Date office acted on the request
postponementApprovalRemarks	TEXT	Office remarks on approve/reject
3c. New API endpoints
Method	Route	Purpose
POST	/work-orders/:id/postpone-request	Submit new postponement request → sets status to "Awaiting Office Approval", writes to work_order_postponements
PUT	/work-orders/:id/postpone-request	Edit and resubmit → retains history, creates new audit row
POST	/work-orders/:id/postpone-approve	Office approves → sets status to "Postponement Approved", applies the new due date
POST	/work-orders/:id/postpone-reject	Office rejects → sets status back to Due or Overdue (based on schedule), records rejection
3d. Service logic changes — workOrderAutoService.ts → checkPostponements()
This cron job currently reverts all Postponed WOs back to Due when their end date is reached. It must be updated to:

Only process WOs with status "Postponement Approved" (not "Awaiting Office Approval" — those should not be reverted until rejected)
When a Postponement Approved WO's end date is reached, revert it to Due or Overdue as appropriate
3e. Approve/Reject service logic
On Approve:

Update work_orders.status → "Postponement Approved"
Update work_orders.dueDate → the requested postpone date (new due date)
Update work_orders.postponementEndDate → postpone date
Write approval record to work_order_postponements (approvedDate, approvedBy, approvalRemarks, status = "Approved")
On Reject:

Update work_orders.status → "Postponement Rejected" temporarily, then immediately recalculate to Due or Overdue using computeWorkOrderStatus() based on the original due date
The WO's dueDate reverts to the original (do not change it)
Write rejection record to work_order_postponements
3f. Audit trail
The existing work_order_postponements table is already the audit table (postponementNumber increments per resubmission). Each action writes a new row:

status column values: "Awaiting Approval" → "Approved" / "Rejected"
Each resubmission increments postponementNumber and creates a new row (old rows remain — full history)
submittedDate, approvedDate, approvedBy, approvalRemarks already exist; just need approver and postponeDate columns added (3a above)
