## 0. P0.1a — which auth path does the production (MFE) build use? (answered before any change)

**READ, cited:** the same one. `server/routes.ts:44` mounts `mockAuthMiddleware` for every `/technical/api` request **unconditionally** — there is no env/build flag selecting another auth path (`grep -rn mockAuthMiddleware server` → the single mount; no `NODE_ENV`/`APP_ENV` branch around it). `server/middleware/auth.ts:92-135` (pre-Phase-0) sets `req.user.role = "Sail Admin"` for every request (`:122`, comment *"RBAC mock — unchanged in Phase 0"*) and stashes the forwarded role only as `forwardedRole` *"for audit attribution only (never consulted by requireRole/RBAC)"* (`:105-108`, `:132-133`). In the multi-tenant production build `tenantMiddleware` (`server/middleware/tenantMiddleware.ts`, inert when `MASTER_DATABASE_URL` is unset) verifies the SAILERP Bearer and resolves the tenant, and explicitly *"does NOT touch req.user / role / RBAC — identity stays with mockAuthMiddleware"* (`:14`, `:77`). The MFE shell contributes identity only as headers (`client/src/lib/activeRank.ts:120-128`, values from the decrypted SAILERP profile in `client/src/contexts/AuthContext.tsx:326-349` — `role` = the SAILERP role name, `userType` = `Office|Ship`).
**Consequence:** `requireRole` / `requirePermission` enforced nothing for anyone in production; the only enforcement was the frontend. **P0.4 is therefore a security fix (API-level), not a cleanup** — the reproduction run's 200s for a vessel-rank caller were real production behaviour.

## 1. P0.1 — server-side role (`8c4e7b088`)

**What changed (path:line at HEAD of the branch):**
- `server/middleware/auth.ts:1-60`: new `RbacIdentity {role, userType, source}` on `req.rbac`; `isMockRbacEnabled()` (`PMS_AUTH_MOCK_RBAC`), `getRbacIdentity()`, `rbacMatches()` (`'Office'`/`'Ship'` match by forwarded user type, every other entry by role name), `RBAC_BYPASS_ROLES` (Sail Admin, PMS Admin). `requireRole` (`:68-86`) evaluates `req.rbac`. `mockAuthMiddleware` (`:156-208`, identity at `:199-207`) resolves `x-user-role` / `x-user-type` onto `req.rbac` (`source: forwarded | mock | none`).
- `server/middleware/permissions.ts`: evaluates the forwarded role name **when a route opts in** (`{ enforce: true }`), optional `{ unconfigured: 'deny' }` (403 `ROLE_UNCONFIGURED`); default = pass-through.
- `docs/LOCAL-TEST-ENVIRONMENT.md` "Identity and roles on the pilot" section; `local-test-env/.env.shore.example` / `.env.ship.example` carry `PMS_AUTH_MOCK_RBAC=0`.

**Two deliberate deviations from the brief's literal wording, and why (both reversible in one place):**
1. **`req.user.role` is NOT overwritten with the forwarded role.** ~40 business-logic call sites read it (RH-cap override `workOrderController.ts:271`, CR/postponement "is Sail Admin" shortcuts, `updateApprovalPolicy` Sail/Super Admin check, `subEntityService` admin-only ops, `documentService` ship visibility, sync `requireOfflineAdmin`, shipskart role mapping …). Switching them all to the real role is a product decision per site, outside "the proven defects only". The real role is on `req.rbac` (and the pre-existing `forwardedRole`).
2. **Legacy guard aliases `requirePMSAdmin` / `requireOfficeOrAdmin` are explicit non-enforcing pass-throughs; `requirePermission` enforces only on opt-in.** Evidence, not opinion: `requirePMSAdmin` (= Sail/PMS Admin only) sits on **60** routes incl. `POST /spares/:id/consume|receive`, stores batch consume/receive, RH config, components sub-entities, rotational items, retention, audit; `requireOfficeOrAdmin` on fleet-admin + noon-report (5). Turning them on with real SAILERP roles would 403 every Vessel User's spare consumption — a regression, not a defect fix. For `requirePermission` (≈150 routes): on the dev-copy DB, configured roles (Super Admin, Admin, Vessel Admin, Vessel User) have `adm_role_menu_access` rows for **~13 menus only** (admin-*, stores, approval-workflow-*) — **none for `change-requests`, `pms-modify-pms`, `admin-masters`** — while the UI gates those screens by different resource names (`ModifyPMS.tsx:139` uses `pms-modify-pms`, the CR routes use `change-requests`); crew create CRs from the WO form / component drawer. Enforcing would 403 crew CR creation and office CR approval. One latent drift also found: `requirePermission('admin-alerts')` matches no active menu name. **Flip when the permission rows are complete:** `requirePermission(..., { enforce: true })` default, and/or re-bind the two aliases to `requireRole([...])`.
3. One route IS newly enforced as a side effect of `requireRole` evaluating real roles: `/fleet/master-list-types` writes (`fleet/routes.ts:9`, `requireRole(['Sail Admin'])` by name) — now Sail Admin only (Office "Admin" → 403). Flagged for Ghazi; revert = one line if Admin users need it.

**Tests:** `server/middleware/__tests__/rbacIdentity.test.ts` — **12/18 failed at HEAD~, 19/19 pass after** (identity resolution incl. `source: none`, mock switch; `requireRole` Office/Admin pass, Vessel User/Vessel Admin/anonymous 403 with `required`/`current`, name-only guard; `requirePermission` pass-through default, Sail Admin bypass w/o DB, configured deny, unconfigured allow vs deny).
**Pilot (P0.1c, `scripts/test-phase0-p01.ts`, shore):** `reviewer-approve` on `PHASE0-L2-278-2026-001` (Pending Office Review): Vessel User → **403** `{"required":["Office","PMS Admin","Sail Admin"],"current":"Vessel User"}`, Vessel Admin → 403, no headers → 403 `current:"anonymous"` (status unchanged), Office "Admin" → **200** → Completed. Regression battery with real roles **12/12 unchanged**: Vessel User GET work-orders 200, GET approval-policy 200, Office Admin PUT approval-policy 200 / GET awc 200 / GET sync settings 200 / POST jobs 201, Vessel User POST change-requests 201, Vessel User spares consume reaches validation (400 qty), Sail Admin fleet overview 200; NEW: fleet master-list-types Office Admin 403 / Sail Admin passes guard. Headerless provisioning scripts still work (`provision.sh` after the ship rebuild: import `success=true`).
**P0.1d — operator check on dev (MFE-integrated), after deploy:** log in as a vessel user → open a locked WO (or call `POST /technical/api/work-orders/<id>/superintendent-acknowledge` from the browser console) → expect **403** `{"current":"<SAILERP role name>"}`; then as an office user → 200.
