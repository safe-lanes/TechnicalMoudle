## 1. Root cause

**Work orders are generated by two independent writers, and each one checks for duplicates —
and picks the running number — using only its own database.**

Two places run the same sweep (`jobDueScanner.runScan`):

- the ship's daily scanner (ship-only, gated by `isShipInstance()` at `routes.ts:140`), and
- the office's **Generate Now** button (`workOrderController.ts:140`).

Both do the same two things, locally:

| Check | Where it looks |
|---|---|
| "does a WO already exist for this job + component?" | `storage.getWorkOrders(vesselId)` — **own DB only** (`jobDueScanner.ts:376`) |
| the running number | `max(existing numbers) + 1` — **own DB only** (`workOrderNumbering.ts`) |

So when the office is missing the ship's work order — exactly what the old dead-letter sync
gap caused — the office sees *nothing* for that job, generates a work order, and numbers it
`-001` because its own set is empty. The ship already used `-001`. Sync then delivers the
office row down and the vessel holds two rows with the same number.

Nothing catches it afterwards:

- `work_order_no` has **no unique constraint** (confirmed in schema + `0000_*.sql`).
- Sync identifies work orders by `wouuid`, so the two rows are two genuinely different
  records. **Sync is behaving correctly — a sync gap enabled the bug, it did not cause it.**

### Why sync raises no conflict (answer to Jeevan)

Conflict detection (`service.ts:882`) builds its key as `table : row-identity : field`, and
for work orders the row identity is `wouuid`. A conflict means *the same field of the same
record* changed on both sides — e.g. ship and office both edited work order X's due date.

When both sides **generate**, nothing is edited. Two separate records are created, each with
its own id. There is no shared record to compare, so there is nothing to flag.

> It is the difference between two people editing the same job card (a conflict sync catches)
> and two people each writing a new job card (two cards — not a conflict). The problem is not
> that sync missed something; it is that two places were allowed to write a card for the
> same job.

### Proof — pilot reproduction (2026-07-31)

Real code, two real databases, WKFV pilot vessel.

| Step | Result |
|---|---|
| Ship holds `MKR-OV-00010-721.003.02-2026-001`; office made blind to it (raw DELETE = no field log = the dead-letter state) | office has 0 rows for that job |
| Office clicks Generate Now | creates **`MKR-OV-00010-721.003.02-2026-001`** — same number, new `wouuid` |
| Sync ship↔office | ship shows **3 rows sharing one number** |
| **Negative control** — repeat with the office *holding* the row | **generated 0** — the check works perfectly *within* one database |

Pilot restored to its exact prior state afterwards (302 WOs both sides).

### Gas Mia evidence (189 duplicate numbers, 378 rows)

- **162 of 189** groups: earlier copy **absent from the office**, later copy in both. A
  repeated number *proves* the generating DB did not hold the other row — so the later copy
  was made in the office.
- Three office generation events: **26-Jun (37), 08-Jul (14), 15-Jul (138)** — discrete
  bursts, i.e. Generate Now clicks. Shore runs no automatic scanner.
- Gap between copies: **9–33 days** — the window when ship→office sync was failing.
- Remaining **27**: same mechanism; the ship's copy reached the office *later* (hardening /
  re-offer back-delivered it) — which is why the office itself now shows exactly 27
  duplicate numbers.
- 154 of the pairs are `Overdue` (ship's original) + `Active` (office's new copy).

## 2. What was rejected, and why

**Instance discriminator in the WO number (S/O prefix) — REJECTED (Jeevan, correct).**
It makes the two rows *look* different; the vessel still receives two work orders for the
same job, now with different numbers, which is arguably more confusing. It fixes the number
collision, not the duplicate — and the duplicate is what the vessel experiences.

**DB unique constraint on `work_order_no` — REJECTED.** Two reasons; the second is serious:

1. It cannot be created while duplicates exist (189 on Gas Mia alone; no fleet-wide count).
2. **It would turn a visible duplicate into silent data loss.** `work_orders` syncs both
   ways. The applier's unique-violation fallback (`oneWayApplier.ts:985`) guesses the
   colliding row from the incoming row's first few non-null columns, **merges the incoming
   fields into it, and rewrites that row's `wouuid`**. A genuinely different second work
   order arriving with a colliding number would be absorbed into the first and the first's
   identity overwritten — one work order quietly gone, instead of two visibly present.

Same principle as the existing CLAUDE.md rule: synced columns must not carry constraints
that reject values arriving from the other side. **Uniqueness belongs at generation time on
a single writer, not in the database.**

**"Refuse if the vessel has unsynced records" — REJECTED as a primary gate.** Weaker than it
sounds; see §3.

## 3. What the office can and cannot know

- **No job-side marker exists.** The scanner writes *nothing* back to the job after
  generating — no "last generated", no work-order link (checked: `jobs` schema + the whole
  scanner). The work order row itself is the only record that one exists. So the office
  cannot ask the job; it can only consult the WO list it already doesn't have.
- **The office cannot ask the ship.** All sync is ship-initiated; shore has no route into a
  vessel. A live "do you already have one?" check is architecturally impossible, not merely
  unbuilt.
- **What the office does have** per vessel (`getFleetSyncOverview`): `last_sync_at`,
  `last_sync_status`, unresolved conflicts, and `pending_changes` — but that last one counts
  the **office's own** unsent queue, not the ship's.
- **"Recently synced" never meant "complete".** During the dead-letter period sync reported
  success while rows were being silently dropped.

Conclusion: a freshness gate would have blocked most of Gas Mia (gaps 9–33 days) but is a
heuristic, not a guarantee. It is not the gate.

## 4. 🔴 THE GATE SIGNAL — and the production check that must pass first

**Signal: does `sync_metadata` hold any row for this vessel?**

Shore mints that row when a **real provisioning bundle is generated**
(`provisioningService.ts:92`) — the ship's instance id plus its minted sync key, keyed to the
vessel. The download endpoint always passes `persist: true` (`controller.ts:540`); previews
do not mint.

This latches at the right moment: **the instant a second writer becomes possible** — not at
first sync, which would leave a window where the ship exists but has not yet called home.

Verified on the pilot: **1 of 18 vessels carries rows** (the provisioned one, with two rows —
the known orphaned-instance-id residue). The other 17 have none.

| | |
|---|---|
| ✅ | Test **row existence**, NOT `instance_id LIKE 'SHIP-%'`. Provisioning notes that legacy production ships kept their original running ids; a prefix test could read a real live ship as un-provisioned and reopen the bug. Existence is prefix-independent. |
| ✅ | Shore keeps **no per-vessel row for itself** (verified on pilot) — so any row means a ship instance. |
| ❌ | **Field logs are NOT usable** — shore writes them for un-provisioned vessels it edits too (verified). |
| ❌ | There is **no provisioning-status column** on `vessels`. |
| ⚠️ | **Not verified against production.** See the query below. **This is the go/no-go.** |

**Design rule: FAIL CLOSED.** Treat every vessel as LIVE unless it can be *positively proven*
never-provisioned.

### The production query (read-only, safe on production shore)

Single `SELECT`, no writes, no locks. Selects **no secrets** — the `sync_api_key` column is
deliberately not touched.

```sql
SELECT
  v.name                                    AS vessel,
  count(sm.instance_id)                     AS sync_metadata_rows,
  max(sm.last_sync_at)                      AS last_sync_at,
  string_agg(DISTINCT sm.instance_id, ', ') AS instance_ids,
  (SELECT count(*) FROM work_orders w
     WHERE w.vessel_id = v.vuuid AND w.data_scope = 'vessel') AS work_orders,
  CASE
    WHEN count(sm.instance_id) = 0 AND max(sm.last_sync_at) IS NULL     THEN 'NEVER PROVISIONED'
    WHEN count(sm.instance_id) > 0 AND max(sm.last_sync_at) IS NOT NULL THEN 'LIVE'
    ELSE 'CHECK ME'
  END                                       AS verdict
FROM vessels v
LEFT JOIN sync_metadata sm
       ON sm.vessel_id = v.vuuid
      AND sm.is_deleted = false
WHERE v.is_deleted = false
GROUP BY v.vuuid, v.name
ORDER BY verdict, v.name;
```

**What must come back:**

1. Every vessel with a ship at sea shows **LIVE**. If any live vessel shows NEVER
   PROVISIONED, **the signal is unsafe** — abandon inference and add an explicit column.
2. The `instance_ids` column, to confirm (not assume) whether legacy ships kept non-`SHIP-`
   ids. Either answer is fine since the gate tests existence.
3. The count of **CHECK ME** rows — those are the override case (§5).

Send the whole table back, not a summary.

## 5. The three verdicts = the three behaviours

| Verdict | Meaning | Direct generation on shore |
|---|---|---|
| **NEVER PROVISIONED** | no bundle ever minted | **Allowed** — Sail Admin, no override needed |
| **CHECK ME** | bundle minted, ship never called home | **Override** — Sail Admin only, audited |
| **LIVE** | ship exists and has synced | **Never.** Request path only, no override at all |

Sail Admin must be able to generate directly on shore for **provisioning** — building the
initial WO data for a new vessel's bundle. At that point no ship exists, so no second writer
exists, so no duplicate is possible. **Role alone is not a safe gate** — a Sail Admin
clicking Generate Now on a live vessel would reproduce the bug unchanged. Hence vessel state
AND role, both.

### Override design (Jeevan's edge case: bundle minted, ship never built)

**Reachable only when `last_sync_at` is NULL everywhere for that vessel.** If a ship has ever
called home, the ship exists and the override is not offered — not to anyone, not with any
reason. It therefore cannot become a back door onto a live vessel.

- **Who:** Sail Admin only — the role that provisions. Not Client Admin, not Head of Dept
  (both of whom can see today's button).
- **Shape:** single-use and time-boxed — authorises **one** generation run, then expires. Not
  a flag that can be set once and left on.
- **Requires** a typed reason; no default.
- **Logged** to the audit trail and to a greppable console / syncDiag line:
  - who invoked it, when, which vessel
  - the typed reason
  - vessel state at that moment — `sync_metadata` row count, `last_sync_at`, existing WO count
  - outcome — how many work orders the run generated

If a duplicate ever traces back to an override, the record says who authorised it, why, and
what the vessel looked like at the time.

## 6. Build order — ⚠️ SUPERSEDED 2026-08-03, kept for the record. See §9.

Item A was built (2026-08-03) and then REDUCED per §9.5. Items B and C (request model +
queued UX) are SUPERSEDED by the §9 reconciler design and must not be built. Item D's concern
(office manual single-WO numbering) is covered by the reconciler's grouping. Item E's
detection folds into the reconciler's telemetry (§9.6).

### A. Server-side gate — DO FIRST, stands alone

`POST /work-orders/generate-now` has **no gate at all today** — proven by calling it
successfully against the ship during this investigation. The UI gate
(`WorkOrders.tsx:1460`, `isShore && (isSailAdmin || isClientAdmin || isHeadOfDept)`) is
presentation only.

Enforce server-side: **Sail Admin AND zero `sync_metadata` rows AND no `last_sync_at`** —
all three. Refusal returns a named reason the UI can display. Plus the §5 override path.

**This alone closes the hole, before the request model lands.**
**Blocked on §4.** Building it before the production numbers would ship a gate that *looks*
safe while still permitting the bug — worse than no gate.

### B. The request model

Generate Now becomes a **request, not a write**, for every non-provisioning case. The office
queues a request; it syncs shore→ship; the **ship** runs the sweep; work orders come back up
the normal path. Only one side ever creates a work order, so the "office was blind" case
cannot arise.

- New table, migration **151** (**144 stays RESERVED** for Phase 1 tri-state; 149 and 150
  are taken).
- Lifecycle: `queued → sent → executed → results-received`, plus `failed` and an expiry so a
  request for a vessel that never calls home does not sit forever.
- Sync surface change — requires explicit sign-off per CLAUDE.md before touching
  `shared/syncConfig.ts`.

**Accepted cost:** the office no longer sees results instantly; it sees them after the next
sync. Jeevan has accepted this.

### C. Office UX for a queued request

- Immediate confirmation that the click was **queued, not done**.
- The vessel's last-sync time shown, so the user knows roughly when to expect it.
- Request state visible on the work-orders screen.
- A clear result when it lands — how many work orders were generated.
- The un-provisioned Sail Admin path stays instant and **says so**, so the two behaviours are
  not confused.

### D. Manual single-WO creation

Same numbering flaw — the office numbers from its own database. In scope, not left as a known
hole: it goes through the same gate, or its numbering is made collision-safe.

### E. Detector

Per-vessel repeated `work_order_no` check, surfaced on the fleet/sync screen and runnable as
a support script. No migration. Independent of everything above — the net if this reopens
another way.

## 9. APPROVED DIRECTION (2026-08-03) — dual writers + post-sync reconciler (Sahil)

Supersedes the request model (§6 B/C). Business requirement driving it: **on VSAT, sync WILL
lag, and if the office sees no work orders the client concludes the system is broken.** So
shore generates on its own once-daily scheduler, the ship keeps its scanner, sync delivers
both copies unchanged, and a shore-side reconciler resolves duplicates after sync.

**Sync stays exactly as it is — wouuid-keyed, applier untouched, no business-key matching.**
The reconciler is a consumer of synced data, not a participant in sync.

### 9.1 Origin — recoverable from sync bookkeeping, NO schema change

`work_orders` has no origin column (checked every column: `is_sync` is a dead column never
written for WOs; `created_by_uuid` identical both sides; the local `id` travels with the row
so `WO-SYNC-*` marks only 6 of 2,890 office rows). But **`sync_field_log.instance_id` retains
it**: row creation is an INSERT-origin log group (`old_value IS NULL`) under the creator's
instance id. Shore stores the ship's pushed logs verbatim (`service.ts:232`) and logs its own
creations (`workOrderService.ts:927` — the scanner goes through it). Proven on the pilot:
ship-created WO → 41 logs, all `SHIP-WKFV`, INSERT-origin group present.

Caveat: synced field-log entries prune after 90 days (default). Irrelevant at daily cadence,
but the rule needs a fallback for a log-absent row (below), never a guess.

### 9.2 Precedence — all three cases AUTO-RESOLVE (approved by Sahil 2026-08-03)

Grouping key: `(vessel_id, work_order_no)` over non-deleted rows — this also resolves the
"which shore copy" ambiguity (shore holding both copies is the designed steady state, the old
"27" pattern made normal). "Touched" = any of: approver, submitted_date, date_completed,
work_carried_out, performed_by, manhours, consumed spare parts, attached documents — or a
persisted workflow status (Completed / Pending Approval / Postponed / Rejected).

1. **Exactly one copy touched** → the touched copy survives, whichever side created it.
   (Gas Mia measured ~50/50 office/ship on where the work landed — origin does NOT predict
   where the work is, so content is the primary signal.)
2. **Neither touched** → the **ship's copy survives** (origin per §9.1). Fallback when the
   INSERT logs are pruned/absent: earlier `created_at` survives.
3. **Both touched** → the **ship's copy survives automatically** — no manual step, no pending
   queue. The office copy is **ARCHIVED AND FLAGGED, not deleted** (§9.3): nothing waits on a
   human, nothing is destroyed, and the office's record (approval, completion, remarks) is
   recoverable if anyone asks where it went.

NOTE on case 3: only the CHILD RECORDS move to the survivor (§9.4). The loser row's own
FIELDS (its status, approver, completion data) do NOT merge into the survivor — they live in
the archive snapshot. A Completed office copy losing to an Overdue ship copy means the WO
reads Overdue afterwards; the completion evidence is in the archive and its children.

### 9.3 The archive — soft delete + field log + NO_SYNC bookkeeping table

- **Soft delete** the losing row (`is_deleted = false → true`) **with an explicit
  `logFieldChanges` call** — work_orders writes are NOT storage-logged (32 manual call
  sites; the postpone-sync lesson). The flip syncs to the ship as a normal field change, so
  both sides converge with the loser hidden.
- **Self-heal safe — verified in code:** `applyFullRowsIfAbsent` exist-checks by identity
  with NO `is_deleted` filter and "NEVER touch[es]" a present row. A soft-deleted row counts
  as present on both sides, so the duplicate CANNOT be resurrected. (**Hard delete is the
  dangerous option** — absent row + inbound logs → self-heal re-delivers it → duplicate
  returns. Plus `work_order_documents` FK is NO ACTION → error, and the other five child FKs
  are unmaterialised in the real DB → silent orphans.)
- **NO_SYNC archive table** (shore-only bookkeeping, migration **151** — 144 stays RESERVED):
  `work_order_reconcile_archive(archive_uuid, vessel_id, work_order_no, loser_wouuid,
  survivor_wouuid, resolution_case 1|2|3, loser_row_snapshot jsonb, child_moves jsonb,
  reconciled_at, notes)`. The jsonb snapshot preserves the loser exactly as archived even if
  the soft-deleted row is later mutated or pruned. NOT in syncConfig (same pattern as the
  Shipskart link tables) — zero sync surface.
- Pure soft-delete alone was rejected: no flag, no survivor pointer, no "where did my
  approval go" answer for support. The archive table is that answer.

### 9.4 Child records — they FOLLOW THE SURVIVOR

All references to the loser's `wouuid` are repointed to the survivor across the six child
tables (documents, executions, execution details, postponements, component maintenance
history, IHM log) plus the four denormalised reference sets (superintendent notifications,
postponement approvals, anomalies, monthly snapshot arrays). Every repoint is field-logged so
the ship converges. `child_moves` in the archive records exactly what moved.

Two consequences to accept, one caveat to prove:

- **Accepted:** in case 3 the survivor can end up with TWO sets of children (e.g. two
  execution records — the ship's and the office's). That is honest evidence of the double
  handling, and the archive row explains it.
- **Accepted:** the loser's own fields do not move (see §9.2 note).
- **⚠️ MUST PROVE AT BUILD TIME:** three of the six child tables have
  `identityColumn: null` in syncConfig (`work_order_documents`, `work_order_executions`,
  `ihm_maintenance_log`). How a repoint UPDATE on those propagates to the ship must be proven
  on the pilot before the reconciler ships — if identity-less updates do not apply cleanly,
  those tables need per-table handling. Do NOT assume.

### 9.5 Item A — REDUCED (not reverted)

Sahil's design requires shore to generate, so the LIVE and CHECK_ME refusals are REMOVED.
Kept, because the endpoint having no gate at all is a separate problem from duplicates:

- unknown-vessel **fail-closed** check (absence of evidence is never evidence of absence)
- the **role restriction** (Sail Admin; enforcement-limited by the RBAC mock — documented in
  the module; becomes real when real auth lands)
- the 403 + named-reason response shape

The provisioning-state seam (`getVesselProvisioningState`) stays: read-only, and the
reconciler/telemetry can use the same verdicts.

### 9.6 Reconciler operational rules

- **Shore only.** All six child tables are BOTH_EDITABLE — running it both sides would
  machine-generate real sync conflicts. Shore resolves; its changes sync down.
- **Between syncs, never during.** Mid-sync it could reattach against a half-arrived picture
  and archive a row whose children land afterwards. It must acquire the same per-vessel lock
  the engine uses (`syncInProgress` / `tryAcquireVessel`, `autoSyncScheduler.ts:329`) and
  skip any vessel sync currently holds.
- **Idempotent and bounded**: re-running on an already-reconciled vessel is a no-op; per-run
  cap with the remainder picked up next run; every action loud in the log.
- **Telemetry**: per-vessel count of duplicates resolved per case, surfaced on the sync/fleet
  screen — office-generated duplicate volume is exactly the signal that would have caught
  Gas Mia in week one.

### 9.7 The shore scheduler (once daily)

- Role resolution via **`schedulerRoleWatchdog`**, NEVER the boot-time `isShip` snapshot
  (the 28-Jul auto-sync root cause). The watchdog starts/stops it on role change.
- Registered in **`stopAllSchedulers`** (routes.ts) — a missed entry orphans on PM2 restart.
- **Per-vessel iteration** (one bad vessel must not abort the sweep), configurable interval,
  and a run lock (the existing 409-style guard).
- Vessels with no ship (the 85): shore is the only writer — nothing to reconcile, safe.

### 9.8 Honest limits (recorded so nobody is surprised)

- The reconciler's cadence does NOT bound exposure — **the vessel's connectivity does**. It
  cannot resolve what sync has not delivered. A week offline = a week where both offices see
  and work their own copy; that window is the price of the availability requirement, by
  design. Gas Mia's gaps were 9–33 days.
- Case 3 (both touched) therefore still happens in steady state — shortened, not eliminated.
  The archive makes it lossless and answerable, not impossible.
- The 189 existing Gas Mia duplicates are **OUT OF SCOPE** — manual one-off cleanup, Jeevan
  decides how. The reconciler handles NEW duplicates only.
